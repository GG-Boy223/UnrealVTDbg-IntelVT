# docs/17 — 0x101 转储实证分析（2026-09-18 崩溃序列）

> 本文是「从静态分析转向实际转储取证」的第一份完整报告。
> 目标转储由用户指定：`F:\001\VT\蓝屏文件\` 根目录下的四个 `091826-*`。
> `Ultral9 275hx\` 子目录下的两个 `0x20001`（HYPERVISOR_ERROR）**不在本轮范围**，
> 相关结论已降级为旁证，不参与本节推理。

---

## 1. 四次崩溃的完整时间线（首次拿到）

四个转储的内核基址两两不同，证明是**四次独立的启动**，不是同一次开机的多次转储：

| 内核基址 | 对应转储 |
|---|---|
| `FFFFF807ED600000` | `091826-10015-01.dmp` |
| `FFFFF80679000000` | `091826-7250-01.dmp` |
| `FFFFF802C1E00000` | `091826-19187-01.dmp` |
| `FFFFF80281000000` | `091826-9843-01.dmp` |

结合 `!analyze -v` 的 `Debug session time` 与 `System Uptime`，得到完整时间线（时区 +8）：

| # | 崩溃时刻 | BugCheck | 本次运行时长 | 推算开机时刻 | 距上次崩溃 |
|---|---|---|---|---|---|
| 1 | **17:07:45** | `0x9C` MACHINE_CHECK_EXCEPTION | 2:17:50 | ~14:49:55 | — |
| 2 | **17:40:02** | `0x101` CLOCK_WATCHDOG_TIMEOUT | 0:30:14 | ~17:09:48 | 重启约 2 分 03 秒后 |
| 3 | **17:51:33** | `0x5` INVALID_PROCESS_ATTACH_ATTEMPT | 0:10:58 | ~17:40:35 | **重启 33 秒后** |
| 4 | **18:06:32** | `0x101` CLOCK_WATCHDOG_TIMEOUT | 0:14:46 | ~17:51:46 | **重启 13 秒后** |

### 结论 1：这是一个崩溃循环

从 17:07 到 18:06 的 59 分钟内，机器崩了四次，**每次重启后 10~30 分钟内必然再崩**。
这个形态本身是强信号：存在一个在开机后固定时间窗口内必然触发的条件，而不是随机偶发。

### 结论 2：BugCheck 码是混合的

同一台机器、同一天，出现三种完全不同性质的蓝屏：

- `0x101` — 某个处理器不再响应时钟中断（挂起核 **6** 和 **9**，两次不同）
- `0x5` — 进程附着失败（触发点在 `nt+0x22066f`，即 attach 路径）
- `0x9C` — 机器检查异常（硬件级）

三种码共存，指向「系统范围内的状态被破坏」或「平台层面不稳定」，而不是单一函数里的单一 bug。

## 2. `0x101` 参数的权威语义

`!analyze -v` 给出的官方释义（这是判据的基础，不是我推测的）：

```
CLOCK_WATCHDOG_TIMEOUT (101)
An expected clock interrupt was not received on a secondary processor in an
MP system within the allocated interval. This indicates that the specified
processor is hung and not processing interrupts.
Arg1: 0000000000000008, Clock interrupt time out interval in nominal clock ticks.
Arg2: 0000000000000000, 0.
Arg3: ffffcc01865db180, The PRCB address of the hung processor.
Arg4: 0000000000000006, The index of the hung processor.
```

| 参数 | 10015 | 7250 | 含义 |
|---|---|---|---|
| Arg1 | `0x8` | `0x8` | 超时间隔（标称时钟 tick 数），两次相同 |
| Arg2 | `0x0` | `0x0` | 保留 |
| Arg3 | `FFFFCC01865DB180` | `FFFFA581C0A00180` | **挂起核的 PRCB 虚拟地址** |
| Arg4 | `0x6` | `0x9` | **挂起核的处理器索引** |

**判据**：`0x101` = 编号 6（或 9）的处理器在超时窗口内没有处理时钟中断。
结合本项目 `external_interrupt_exiting = false`（时钟中断直接投递来宾、不经 VMM），
等价于：**该处理器没有回到来宾执行时钟 ISR**。

## 3. 我实际从转储里挖到了什么

### 3.1 挂起核的 PRCB —— 定位成功，但只保留第一页

`0x101` 的 Arg3 直接给出挂起核 PRCB 的虚拟地址。转储里**确实包含这页内存**，
我用 `db` 读出来并做了双重校验：

| 偏移 | 10015（挂起核 6） | 7250（挂起核 9） | `_KPRCB` 字段 |
|---|---|---|---|
| `+0x000` | `80 1F 00 00` | `80 1F 00 00` | `MxCsr = 0x1F80`（默认值） |
| `+0x004` | **`06`** | **`09`** | `LegacyNumber` = 处理器号 |
| `+0x005` | `00` | `00` | `ReservedMustBeZero` |

两处处理器号与 Arg4 完全一致 → **确认这就是挂起核的 PRCB**（PRCB 位于 `KPCR+0x180`，
地址末三位为 `180`，与结构定义吻合）。

**但转储只保留了 PRCB 的第一页**：

```
已收集 PRCB 内存: 0xFFFFCC01865DB180 .. 0xFFFFCC01865DC000  (3712 字节)
```

`3712 = 0x1000 - 0x180`，即恰好到页边界为止。挂起核保存的寄存器现场
（`_KPROCESSOR_STATE` / `_CONTEXT`，含 `Rip`、`Rsp`）位于 PRCB 更靠后的位置，
**不在转储里**。因此「挂起核当时正在执行谁的代码」这个问题，
**用当前这种转储类型无法回答**。

### 3.2 挂起核 PRCB 里没有指向 VT_Driver 的引用

对已捕获的 PRCB 首页做全量指针扫描，比对当次启动的 `VT_Driver` 镜像范围：

| 转储 | VT_Driver 镜像范围 | PRCB 内指向该范围的指针 |
|---|---|---|
| 10015 | `[FFFFF807A4040000, FFFFF807A4C5F000)` | **0 个** |
| 7250 | `[FFFFF8062F090000, FFFFF8062FCBA000)` | **0 个** |

两个 PRCB 首页结构完全一致（同偏移处的指针仅随 nt 基址平移），
其中出现的指针全部指向 `nt` 自身。**在已捕获的这一页里，没有我们的驱动。**

> 注意：这是**有限结论**。首页不含引用 ≠ 挂起核不在我们的代码里——
> 因为判据（Rip/Rsp）在未捕获的那部分。

### 3.3 `0x9C` 的 `MCA_EXCEPTION` —— 空记录

`0x9C` 的 Arg2 是 `MCA_EXCEPTION` 结构地址。读出来是：

```
FFFFCD81673B6B20  01 00 00 00 00 00 00 00 | 1E 0E 06 2B 4D 47 DD 01
FFFFCD81673B6B30  01 00 00 80 00 00 00 00 | 00 00 00 00 00 00 00 00
FFFFCD81673B6B40  00 00 00 00 ... （其后 0xE8 字节全为 0）
```

| 字段 | 值 |
|---|---|
| `Version` | `1` |
| `TimeStamp` | `0x01DD474D2B060E1E` → **2026-09-18 17:07:45 (+8)** |
| `ExceptionType` | `0x80000001`（高位置位 = 致命；与 Arg1 相同） |
| `BankNumber` / `MCA Address` / `MCi_STATUS` | **全部为 0** |

**现代 Intel CPU 上一次真实的不可纠正机器检查，必然填充 `MCi_STATUS`
（以及 bank 号，通常还有出错地址）。这条记录里这些字段全空。**

另外这次转储的特征也和其他三次不同：

| 转储 | `DUMP_FILE_ATTRIBUTES` | 大小 | 栈 |
|---|---|---|---|
| 10015 / 7250 / 9843 | `0x20008` | 3.5~4.2 MB | 有若干帧 |
| **19187 (0x9C)** | **`0x11008`** | **0.23 MB** | **仅 `nt+0x4fd130` 一帧** |

`0x9C` 这次几乎什么都没抓到，栈是空的。这与「系统在写转储前就已经无法正常工作」相符。

### 3.4 `0x5` 的触发点

`0x5` 的栈显示 bugcheck 由 `nt+0x22066f` 抛出（attach 路径），
即某处调用了进程附着但目标进程不可附着。Arg1 / Arg2 是两个内核对象地址
（`FFFFCE08115E9080` / `FFFFCE07FB6DD040`）。读 Arg1 指向的结构，
`_DISPATCHER_HEADER.Type = 3`（ProcessObject），且 `WaitListHead` 自指
——符合「进程处于早期初始化或正在终止、尚不可附着」的形态。

**但调用方（哪个驱动发起的 attach）不在 triage 转储的栈里。**

## 4. 环境：四个 VT-x 争夺者

四次崩溃的模块列表高度一致（240 / 241 / 236 / 239 个模块）。其中值得注意的：

| 类别 | 模块 | 四次是否都在 |
|---|---|---|
| **本项目** | `VT_Driver`、`DbgkSysWin11` | ✅ 全在 |
| **其他 hypervisor** | `vmx86`（VMware Workstation） | ✅ 全在 |
| | `LdVBoxDrv`、`Ld9BoxSup`（雷电模拟器 / VirtualBox） | ✅ 全在 |
| | `winhvr`、`hvservice`（Windows Hyper-V 根分区） | ✅ 全在 |
| | `vmci`/`VMNET`/`vmnetadapter`/`vmnetbridge`/`vmnetuserif`/`vmusb`/`vsock`/`hcmon` | ✅ 全在 |
| **反作弊** | `ACE_BASE`、`ACE_ADVT`、`ACE_SSC_DRV64`（腾讯 ACE） | 前三次全在，第 4 次少了后两个 |
| **安全软件** | `sysdiag`、`360Sensor_DM64`（360）、`hrwfpdrv`、`hrdevmon`、`UnionFS`、`SunnyFilter2`（火绒） | ✅ 全在 |
| **硬件/远程** | `HWiNFO_x64_215`（直接读写 MSR）、`nvlddmkm`、`OrayVGC`/`OrayUSBVHCI`（向日葵）、`ToDesk` | ✅ 全在 |

**关键点：VT-x 只能有一个主人。** 这台机器上同时装着我们的驱动、VMware 的 `vmx86`、
雷电的 `LdVBoxDrv`，以及 Windows 的 `winhvr`；再叠加腾讯 ACE 的三个内核模块
（ACE 本身以检测/对抗第三方 hypervisor 为目的）。

这是本项目所有目标平台里**最恶劣的一种运行环境**。任何一次「另一个 hypervisor
在某个处理器上执行了 VMXON / VMCLEAR / 抢走了 VMCS」，都会让我们的
VM-exit 路径直接失效——而 `0x101` 正是「处理器回不到来宾」的表象。

## 5. 转储的能力边界（为什么现在还不能定论）

必须说清楚当前证据的极限，否则后面的结论会站不住：

1. **Triage 转储不含挂起核的栈。** 四次转储的栈底都是同一个 `nt+0x4fd130`
   （bugcheck 分发器），挂起核的调用栈不在其中。
2. **PRCB 只保留第一页（实测 3712 字节）**，寄存器现场在未捕获部分。
3. **符号不匹配且无法补齐。** `F:\symbols` 里缓存的 `ntkrnlmp.pdb` 与崩溃内核
   不是同一个构建，调试器报 `WRONG_SYMBOLS_X64_TIMESTAMP_180425-011150_5ADFD5D6`；
   本环境网络不通（`schannel: failed to receive handshake`），无法从微软符号服务器补下。
   因此 `nt+0x269e8b`、`nt+0x22066f`、`nt+0x4fd130` 这些偏移**无法解析成函数名**。
4. **没有崩溃那台机器的加载日志。** `C:\VTLoad.log` 是**另一台 12 逻辑处理器的机器**
   （本机 `os.cpu_count() = 12`），而崩溃机是 **24 处理器**。两者不能混用。

## 6. 假设排序

### H1（优先）—— 处理器进入 VMX root 态后没有返回

`0x101` 的直接语义就是「处理器没回到来宾」。本项目 `docs/10` 已穷举 12 条通路
（P1~P12），其中 P8（pending MTF + VMCALL 互等）与 P10（未处理 EPT violation
的限次失效导致无限往返）已经修复。剩余候选：P7（`wait_for_page_quiescence` /
`wait_for_function_quiescence` 无上限忙等）、P11、P12。

支持：崩溃点固定在开机后 10~30 分钟，符合「某条路径被稳定触发」。
不支持：**挂起核每次不同**（6 和 9）。软件死锁通常挂固定的核或固定的一组核。

### H2（优先）—— 其他 hypervisor / ACE 抢占 VT-x

支持：机器上确实有 4 个 VT-x 使用者；ACE 的存在使「外部代码主动干预 VMX 状态」
成为现实可能；`0x101` + `0x5` + `0x9C` 混合出现，符合「状态被外部破坏」。
不支持：暂时没有直接证据（转储里看不到挂起核的状态）。

### H3（必须保留）—— 平台/硬件层面不稳定

支持：`0x9C` 的 `MCA_EXCEPTION` **完全没有 `MCi_STATUS`**，是反常的；
`0x9C` 那次几乎没抓到任何现场；四次连崩、挂起核每次不同。
不支持：暂无更多硬件侧证据（需要 `!errrec` / WHEA 事件日志，两者都依赖符号）。

**当前证据不足以在三者之间定论。** 下面给出能定论的实验。

## 7. 决定性下一步（需要你配合）

### 7.1 改转储类型为「完整内存转储」——这是最关键的一步

当前四次都是 **Kernel Generated Triage Dump**，它按设计**丢弃挂起核的栈和大部分 PRCB**。
把崩溃机的转储类型改成完整转储后，下一次 `0x101` 就能直接看到挂起核的 `Rip`/`Rsp`：

```
系统属性 → 高级 → 启动和故障恢复 → 设置 → 写入调试信息 → "完整内存转储"
（或注册表 HKLM\SYSTEM\CurrentControlSet\Control\CrashControl\CrashDumpEnabled = 1）
```

有了挂起核的 `Rip`/`Rsp`，判定立刻收敛：
- `Rip` 落在 `VT_Driver` 镜像范围内 → H1 成立
- `Rsp` 指向我们每核 root 栈（非分页池）而 `Rip` 在来宾 → H1 的变体
- `Rip`/`Rsp` 都是正常来宾内核栈 → H1 被排除，转向 H2/H3

### 7.2 做一次「不加载驱动」的 A/B 对照

这是成本最低、信息量最大的实验：

- **A 组**：正常开机，**不加载 `VT_Driver`**，照常用机 1 小时以上。
- **B 组**：加载驱动并跑调试器。

若 A 组仍崩 → 与本驱动无关，应转向 H2/H3（平台、其他 hypervisor、反作弊）。
若 A 组稳定、B 组崩 → H1 成立，按 `docs/10` 的 P1~P12 继续收敛。

### 7.3 采集崩溃机的 `C:\VTLoad.log`

需要那台 24 核机器的日志，重点看三行：

- `全平台MAXPHYADDR最大值=xx位 物理上界=0x...`
- `映射规模：PDPT=... PML4=... CoverageGB=...`
- `已扫描N个逻辑处理器` 是否为 24

（本机日志是 12 核机器的，`PDPT=512 PML4=1 CoverageGB=512` 属于该机正常值。）

### 7.4 调试期间关掉竞争的 VT-x 使用者

在排查 `0x101` 期间，建议：关闭 Hyper-V/VBS（`bcdedit /set hypervisorlaunchtype off`）、
不运行 VMware 虚拟机、不运行雷电模拟器、不运行 ACE 保护的游戏。
这样能把 H2 从变量里去掉，让 H1 的复现变得干净。

### 7.5 补符号

`F:\symbols` 里的 `ntkrnlmp.pdb` 与崩溃内核不匹配。需要：
- 在能联网的机器上用 `symchk` 拉取 `ntkrnlmp.pdb` / `hal.dll`（按转储里 nt 的
  PDB GUID + age 精确匹配），或
- 把转储拷到有网络的机器上直接分析。

补齐后 `nt+0x269e8b`（`0x101` 的 bugcheck 调用点）和 `nt+0x22066f`（`0x5` 的调用点）
就能解析，`!prcb` / `!thread` / `!errrec` 也才能工作。

## 8. 本轮代码改动

### 8.1 已修改：`hv::vmread()` 未初始化返回值（`VT_Driver/HypervisorRoutines/HypervisorVmcsAccess.cpp`）

**依据（Intel SDM）**：`VMREAD` 失败（VMfailValid / VMfailInvalid）时
**不会修改目标操作数**，目标保留原值。

**原实现**：

```cpp
unsigned __int64 vmread(unsigned __int64 vmcs_field)
{
    unsigned __int64 value;            // 未初始化
    __vmx_vmread(vmcs_field, &value);  // 返回码被丢弃
    return value;                      // 失败时返回栈上残留内容
}
```

**问题**：返回的是一个**看起来完全合理的伪造值**。而本函数恰好是 VM-exit 快照的
唯一来源——`VmExitDispatcher.cpp:206-208` 的 `EXIT_QUALIFICATION`、`GUEST_RIP`，
以及 `VmExitEpt.cpp:27` 的 `GUEST_PHYSICAL_ADDRESS` 全部走它。
一旦 VMREAD 失败，失败会以「一个正常数值」的形式流入后续判定与致命错误记录，
使真正的故障变成无法诊断的错误现场。

**修改**：初始化为 0 并保留返回码语义（失败时得到显式的 0，而不是栈垃圾）。

> 说明：仓库里其实已经有严谨的封装——`VmExitCommon.cpp:44` 的 `try_vmread()`
> 和 `VmExitDispatcher.cpp:21` 的 `read_vmresume_snapshot_field()` 都检查了返回码。
> 问题在于**热路径用的是最不严谨的那个**（`hv::vmread(` 68 处调用点，
> 加上同命名空间内的裸 `vmread(` 共约 247 处）。

### 8.2 已记录、不在本轮范围的发现

`Ultral9 275hx\` 两次 `0x20001`（Arg1=7，unhandled EPT violation）记录到
`GPA = 0x3FFAF000C60`、`qualification = 0xD81`（按 SDM 位域解码为
「内核态线性地址的读访问、目标 GPA 是线性地址翻译结果、EPT 条目 R/W/X 全 0」）。
该地址需要 42 位物理地址，而 `VmmContext.cpp:199` 把 EPT 客户机物理覆盖范围
算成 `1 << MAXPHYADDR`（MAXPHYADDR=39 时仅 512GB）。
**这条线索与本轮四次崩溃无关**（不同日期、不同机器分组），仅作为旁证记录，
不参与本轮结论。
