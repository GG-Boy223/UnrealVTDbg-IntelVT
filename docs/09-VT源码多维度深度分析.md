# 09 VT 源码多维度深度分析

本文是对 `VT_Driver`（VMX root 态，约 1.97 万行）＋ `DbgkSysWin10/11`（guest 态调试子系统）＋ `Common/Ring0`（公共库）的**多维度**逐行分析，并与主流开源 VT 实现横向对照。

## 0 方法论：为什么要多维度

上一版 `docs/08` 只从「0x101 单点」切入，结果**得出了一个错误结论**（见 §11 修正记录：跨核 INVEPT 缺失）。教训是：

- **单点视角会把「局部看起来错」的东西判成缺陷**，因为它看不到调用方的补偿逻辑（`EptWatchActivation.cpp` 只做本核 INVEPT，但 Dbgk 侧广播路径会让**每个核**都各做一次）。
- **单点视角也会漏掉「跨模块才成立」的缺陷**（`_MINIMAL` 被头文件无条件定义 → 非精简分支成死代码 → MSR 拦截策略与注释意图相反）。

因此本文按 **7 个维度** 独立推进，每维度都要求「文件:行 + 依据」，最后再交叉验证、归并去重。

维度划分：

| 维度 | 关注点 |
| --- | --- |
| A | 架构与数据模型（每核 EPT vs 全局锁的内在矛盾） |
| B | VMX 启动链与 VMCS 层 |
| C | EPT 与 Hook/Watch 全链 |
| D | VM-exit 分发与事件注入 |
| E | 同步原语与锁序 |
| F | 生命周期、资源与释放策略 |
| G | 平台/系统兼容性 |
| H | 与开源实现横向对照 |

## A 架构与数据模型

### A1 核心矛盾：数据模型是「每核独立」，同步模型却是「全局共享」

- 数据侧：每个 `__vcpu` 挂自己的 `__ept_state`（`Vmm/VmmVcpu.cpp` 的 `init_vcpu()` / `init_vcpu_ept()`），每核各自建 EPT、各自读 `IA32_VMX_EPT_VPID_CAP` 与 `CPUID.80000008H`（`Vmm/VmmProcessor.cpp:94`）。这是**正确的 per-processor 模型**。
- 同步侧：安装/删除 Hook/Watch 却用**一把全局** `eptWatchTransaction_lock`（`VmcallDispatch.cpp:91/105/122/188/240/307`、`EptWatchActivation.cpp:27`、`EptWatchBreakpointInstall.cpp:47`、`EptWatchDeactivate.cpp:116`）。

结果：**本可并行的「每核改自己的 EPT」被强制串行化**，而且串行化的那段时间是在 VMX root + IPI_LEVEL（见 E）。

对照：HyperPlatform 的 `EptData` 注释直接写着 `// EPT related data stored in ProcessorData`，其 `ept.cpp` **没有任何自旋锁**，唯一同步是 `InterlockedIncrement(&preallocated_entries_count)`。本项目的 EPT 数据结构与之一致，同步却退化了一级。

### A2 控制面拓扑：guest 驱动 → IPI 广播 → 根态

控制面全部经 `KeGenericCallDpc`（`DbgkSysWin10/11/Hvm/HypervisorGatewayApi.cpp` 共 30+ 处）。这是「一个线程驱动全系统 EPT 变更」的星形拓扑，所有核在同一时刻被拉到 IPI_LEVEL 并进根态。详见 §E3 与 §H6。

## B VMX 启动链与 VMCS 层

### B1【P0】CR4 虚拟化形同虚设 → LA57 场景下 EPT 翻译全错

**已直接核对**（`Vmcs/VmcsGuest.cpp:72-74`）：

```cpp
hv::vmwrite<unsigned __int64>(GUEST_CR4, __readcr4());
hv::vmwrite<unsigned __int64>(CR4_READ_SHADOW, __readcr4() & ~0x2000);
hv::vmwrite<unsigned __int64>(CR4_GUEST_HOST_MASK, 0x2000);   // 仅监视 VMXE 位
```

按 Intel SDM Vol3C 25.1.3，guest 执行 `MOV CR4` 时，**只有当写入值与当前值在 guest/host mask 覆盖的位上不同**才产生 VM-exit。掩码只有 VMXE(bit13)，因此：

- guest 置 `CR4.LA57`(bit12)、`CR4.PCIDE`(bit17)、`CR4.CET`(bit23) 等**都不产生 VM-exit**，硬件直接更新 guest 的 CR4 状态；
- 于是 `VmExit/VmExitControl.cpp:147-158` 里针对 LA57 / CET / PCID 首次开启的合法性校验**全部不可达（死代码）**。

**真实后果**：guest 一旦启用 5 级页表，而 `Globals/GuestMemory.cpp:12-93` 的 `gva2gpa()` 仍用 4 级结构 `pml4_virtual_address`（定义在 `Globals/GlobalsVmmContextTypes.h:218-229`）解析地址 → **把 PML5 当 PML4 走表**，EPT Hook / Watch / 断点隐藏的 GPA 全线算错，且不会报错（只是静默指向错误物理页）。若来宾以 LA57 启动（大内存或注册表开启），驱动加载即进入此状态。

### B2【P0】`_MINIMAL` 被头文件无条件定义，导致 MSR 拦截策略与设计意图相反

`Vmcs/VmcsFields.h:7`、`vmcs.h:21` 无条件 `#define _MINIMAL` → 非精简分支全部是死代码（`docs/04` 的 B10 已证明该分支曾编译不过）。

连带后果（`Vmcs/VmcsControls.cpp:128`）：精简模式下 `use_msr_bitmaps` 仍为 `true`，但位图只拦截 `IA32_FEATURE_CONTROL` 一位，**WRMSR 实际上不被拦截**，于是：

- `VmExit/VmExitMsr.cpp:113-167` 里「PAT / EFER / MTRR 写入 → 同步 `update_ept_memory_type`」这条链**永不执行**；
- 注释声明的意图（MTRR 改动需刷新 EPT 内存类型）无法成立。

反向风险：一旦有人删掉该 define，`Vmcs/VmcsFill.cpp:26` 的 `memset(&vcpu->msr_bitmap, 0xff, PAGE_SIZE)` 立刻变成**全 MSR 拦截**，行为与性能剧变。

### B3【P0】Host CR3 的 PCID 别名问题

`Vmcs/VmcsHost.cpp:26-31` 构造 `host_cr3.flags = 0`（PCID=0），而 `HOST_CR4` 继承 guest 的 `PCIDE`（仅清 LA57/CET/PKS，见 `:43-46`）。

TLB 以 **PCID** 而非 CR3 标记条目。guest 在 PCID 0 下的翻译与 host 不可区分。`docs/01` 第 3 节「补映射后不做 TLB 失效」的理由只覆盖了「同 CR3 内 not-present→present」，**漏了 PCID 别名**这一情形。更关键的是：物理直映窗口被放在**用户半区** `PML4[255]`（`Globals/Globals.cpp:41,44`），guest 用户态同址映射会让 root 读到错误物理页。

建议：Host 使用独占 PCID，或清 `HOST_CR4.PCIDE`。

### B4【P0/P1】物理直映仅 512GB，且多处裸解引用无边界检查

- `Globals/GlobalsConstants.h:21` 固定 512 个 1GB 项（512GB）；`Globals/HostTables.cpp:40-44` 明确拒绝超范围补映射。
- 但 `Globals/GuestMemory.cpp:17/31/55/79`（页表四级）与 `Globals/MtrrMemoryTypes.cpp:143/199` 直接 `host_physical_memory_base + pa` **裸解引用**，无同型判断。
- 对比：`Cr3/Cr3TrackerAddressing.cpp:20/37` **有** `kHostPhysicalLimit` 检查——同一风险两处口径不一致。

内存/页表 PFN 超过 512GB 时根态缺页 → 直接崩（`memcpy_safe` 只保护数据拷贝，保护不了这些解引用）。

> 注意与 `docs/04` B16 区分：B16 解决的是「EPT 覆盖范围」，这里是「Host 直映窗口范围」，是两个不同的 512GB。

### B5【P1】CR0 全掩码 + 禁止关 PG

`Vmcs/VmcsGuest.cpp:61` 把 `CR0_GUEST_HOST_MASK` 设为全 1（guest 任何 CR0 写都 VM-exit），而 `VmExit/VmExitControl.cpp:88` 对 `paging_enable == 0` 一律注入 `#GP`。**guest 无法关闭分页**——休眠/恢复、某些内核路径会写 CR0，需确认是否可接受。

### B6【P1】注入会被静默丢弃

- `HypervisorRoutines/HypervisorInterrupts.cpp:30-33`：检测到已有 pending 事件就直接 `return`，**调用方无法感知**。
- `VmExit/VmExitDispatcher.cpp:257-261`：先做 IDT-vectoring 重注入占位；同一次 exit 内后续需要注入的 `#GP`（如 `VmExit/VmExitMsr.cpp:87`）就被吞掉。SDM 无此合并语义。
- `VmExit/VmExitException.cpp:188-191` 的 `inject_single_step` 排在 IDT-vectoring 重注入之后 → #DB 被吞。

### B7【P1】`vm-exit.asm` 无条件恢复 DR0-DR6

`ASM/vm-exit.asm:121-130` 无条件 `mov dr0..dr6`。guest 置 `DR7.GD` 时（SDM 17.2.1），root 访问调试寄存器会触发 `#DB`，落到 `Tables/idt.cpp:98-104` 的三重故障路径。

### B8【P2】位域与硬编码

- `Processor/msr.h:47-48`：`senter_local:6`（应为 8-13）/`senter_global`（应为 14）与 SDM 的 `IA32_FEATURE_CONTROL` 布局错位（SENTER 在 7/8，SGX 15-18，LMCE 20）。VMX 位（0/1/2）正确，仅影响伪装值。
- `Vmcs/VmcsHost.cpp:90-92`：`HOST_IA32_SYSENTER_*` 硬编码 0，而非继承真实值。

### B9 已核对为「设计如此」

- `ajdust_controls` 的 `ctl &= high; ctl |= low` 正确（`msr.h:13-21`：low=必须为 1，high=可为 1）。
- `VMCS_LINK_POINTER=MAXULONG64`、VMCLEAR/VMPTRLD 用 VMCS 物理地址、revision_id 取自 `IA32_VMX_BASIC`、4KB 对齐由 `alignas(0x1000)` 保证（`Globals/VmxState.cpp:8,17-18,86-92`）。
- `HOST_RSP` 的 `-8` 与 `guest_context.$xmm0` 偏移 0xB8 配套，恰好让 `movaps` 16 字节对齐（注释措辞不准，实现正确）。
- 亲和性绑定与失败回滚对称（`Vmm/VmmEntry.cpp:38-59`、`Vmm/VmmProcessor.cpp:130/147/154/173`）。
- 异常位图全 0 与 IDT-vectoring 重注入自洽（NMI 走 pin-based `nmi_exiting`）。
- `Processor/` 下**无按代际/型号分叉**，全走 MSR/CPUID 能力判定（`Vmm/VmmProcessor.cpp:68-75` 仅日志用）；真正的硬编码是容量常量（512GB 直映、MTRR 345 项、MMIO PD 池 128）。

## C EPT 与 Hook/Watch 全链

### C1【P0】池耗尽时在根态同步分配

`PoolManager/poolmanager.h:130-136`：`request_pool(intention, new_pool=true, size)` 若扫不到空闲池，会同步 `request_allocation` + `perform_allocation` → `allocate_pool_entries`（`PoolAllocation.cpp:56/71/83`）→ `ExAllocatePool*`。

而 hook/watch 安装（split、跳板、`__ept_hooked_page_info`）全走这条路。这与作者自述约束直接冲突（`Ept/Build/EptPageTables.cpp:659`「VM-exit 路径只做纯内存写入，不分配内存」），且该上下文常由 `KeGenericCallDpc` 拉起（IF=0）。HyperPlatform 的做法是池耗尽直接 bugcheck。**应改为耗尽即失败，禁止隐式分配。**

### C2【P0】`unhook_all_functions` 系统性泄漏

`Ept/Hook/Cleanup/EptHookCleanup.cpp:181-244` 只 `remove_hooked_function` / `remove_hooked_page`，**不** `release_pool`：页记录、函数记录、first_trampoline 全部不回收（与 `unhook_function` 的 `:78/128-132` 不对称）。

注释称「driver unload 时 pool manager 会整池释放」——但该函数由 `VMCALL_EPT_UNHOOK_FUNCTION(parameter1 != 0)` **运行期可达**（`VmCall/VmcallDispatch.cpp:109`、`HypervisorGateway/hypervisor_gateway.cpp:158-164`）。每调用一次泄漏 N×100 条，多次调试会话后必然触发 C1。

### C3【P1】跨核 INVEPT —— 原判断已证伪（见 §11）

正确路径是「改表核 → 全核屏障 → **逐核各自 INVEPT**」（`DbgkSysWin11/Hvm/HypervisorGatewayBroadcast.cpp:261-277`），刷新是完整的。

**残留风险（P2）**：
- 若有旁路绕过网关直接 `__vm_call`（如 `Hook/vmx/vmx.cpp:59` 一类路径），会退化成「改他核 + 只本核刷新」；
- `transaction_status != 1` 时全核都不刷新，回滚不彻底会残留中间权限。

### C4【P1】同页 INT3 的已提交 0xCC 会被抹掉

`Ept/Watch/EptWatchBreakpoints.cpp:265-273` 重同步时用真实页覆盖整页伪页，清掉**其它**断点已写入的 0xCC；而安装路径只为新 ID 调 `commit_hide_cc_breakpoint`（`:162-176`），不像 MTF 收尾那样重写全部（`VmExit/VmExitException.cpp:169-176`）。→ 同页多断点场景下先装的断点会失效。

### C5【P1】INT3 双视图不自洽

int3 条目 R/W=1、X=0（`EptWatchBreakpoints.cpp:143-153`），来宾**写**该页不产生 EPT violation，故 `fake_page_needs_full_sync` 只在「同页另有写 watch」时才置位（`Ept/Watch/EptWatchEvents.cpp:238-241`）。来宾修改代码后，执行视图仍是旧内容。属设计取舍，但应显式记录该限制。

### C6【P1】回滚守卫失效且忽略返回值

`Ept/Watch/EptWatchActivation.cpp:159-168` 的 `page_already_rolled_back` 读取的是**已被置 0 的** previous 条目（`:189` 先清零），恒为 `false`；`:175-183` 完全忽略 `ept_watch_deactivate_internal` 的返回值，与 `EptWatchDeactivate.cpp:269-276`「失败即 `KeBugCheckEx`」口径不一致。当前因「每 ID 独占一页」侥幸无害。

### C7【P2】无意义的边界判断（应删，符合作者「不要无意义边界判断」要求）

| 位置 | 问题 |
| --- | --- |
| `Ept/Hook/Instruction/EptHookInstruction.cpp:307` | 跳板是独立缓冲，该判的是 `hooked_instructions_size + kAbsoluteJumpSize <= kTrampolineBufferSize(100)`；现有式子对任何缓冲区都无约束 |
| `Ept/Hook/Instruction/EptHookInstruction.cpp:292` | `> PAGE_SIZE - 1` 差一字节，应 `>= PAGE_SIZE` |
| `Ept/Hook/Instruction/EptHookFakePageMemory.cpp:25/57`、`Ept/Watch/EptWatchBreakpoints.cpp:32`、`VmCall/VmcallDispatch.cpp:175` | `page_offset >= kEptPageSize` 由 `& 0xFFF` 保证恒假 |
| `Common/Ring0/Hvm/EptCoveragePolicy.h:39` | 溢出分支：`highest_end <= 2^52`，死分支 |

**必要、应保留的边界判断**：`Ept/Build/EptAddressing.cpp:17/28`、`EptPageTables.cpp:713`、`Cr3/Cr3TrackerAddressing.cpp:20`、`EptHookInstruction.cpp:33/42`、`EptWatchBreakpoints.cpp:219`、4 级 EPT 的 2^48 裁剪。

### C8 已核对为「设计如此」

- `pml2_pages[i] == nullptr` 的所有使用点均已判空（`EptAddressing.cpp:28`、`MtrrMemoryTypes.cpp:125/174`、`HostTables.cpp:807`、`EptPageTables.cpp:203/612`）；该约定同时表示「1GB PDPTE 大页」与「未补映射 MMIO 空洞」，两者都只需跳过/失败返回，语义自洽。
- 每核独立建表 + 每核读 `IA32_VMX_EPT_VPID_CAP` / CPUID 正确；1GB 能力按核、不支持退 2MB 池（`EptPageTables.cpp:442-501`）正确；MMIO 按需映射写序（mfence 后发布 PDPTE）正确。
- **split 引用计数配对完整**：成功路径 +1（`EptHookDefault.cpp:234`、`EptHookCc.cpp:240`、`EptHookVmcall.cpp:238`、`EptHookInt1.cpp:245`、`EptWatchPageInstall.cpp:152`、`EptWatchBreakpoints.cpp:377`），移除 -1（`EptHookCleanup.cpp:135/242`、`EptWatchDeactivate.cpp:95`）；「已存在页」不 +1 也正确。合并条件（`EptRuntimeSplit.cpp:105-110`）校验了 PDE 仍指向该 split、ref==0、512 项同质，正确。
- 池意图 / `recycled` 复用语义正确（`poolmanager.h:112-114`）。
- **`second_trampoline_address` 是死代码**：全仓库只有读（`EptHookCleanup.cpp:73/137`），无任何写入点 → `unhook_function` 的「递归卸载第二跳板」分支永不执行。

## D VM-exit 分发与事件注入

### D1【P0】MTF 生命周期不闭合 → exit 风暴 → BSOD

`VmExit/VmExitEpt.cpp:60-63、72-75、86-89` 与 `Ept/Watch/EptWatchInt3Execute.cpp:70-73`：`mark_pending_mtf_page` 返回 `false` 时直接 `goto handled_return` / `return`，但 **EPT entry 没有 swap**，硬件仍 `execute = 0` → guest 重试同一指令 → 反复 violation；`removing` 置位后 `acquire_page_hot_reference` 失败走 unhandled，同 GPA+qualification 累计 64 次即 `vmx_fatal_error`（`VmExitEpt.cpp:188-191`）。

对照 SDM Vol3C §25.5.2 与 DdiMon（`shadow_hook.cpp`）：**「改表项」与「置 MTF」必须在同一 handler 内顺序紧邻**，恢复路径幂等。当前实现把两者拆到了 `EptWatchEvents.cpp`（`RestoreEptPageProperties` 里 `set_mtf(true)`）与 `VmExitEpt.cpp`（`mark_pending_mtf_page`）两个不同临界区，配对可失败。

### D2【P0】guest 故障被升级为宿主蓝屏

`VmExit/VmExitException.cpp:219-234` 的 triple fault / VM-entry failure 一律 `vmx_fatal_error` → `KeBugCheckEx`（`VmExit/VmExitCommon.cpp:173`）。

对照 HyperPlatform：`VmpLaunchVm` 里 VMLAUNCH 失败是**读 `kVmInstructionError` 记日志 + 返回错误并清理，不蓝屏**；只有 VMRESUME/VMXOFF 这类宿主侧不可恢复失败才 bugcheck（`vmm.cpp:VmmVmxFailureHandler`）。**guest 的三重故障应终止 guest，而不是把宿主也带走**——对调试器这类工具尤其致命，因为「被调试程序崩溃」是常态而非异常。

### D3【P0】未处理 EPT violation 64 次即 BSOD

`VmExit/VmExitEpt.cpp:188`：MMIO 未覆盖、并发卸载竞态都可能触发，fail-fast 掩盖了真实原因（`docs/04` B16 就是这一类）。

### D4【P1】default 分支注入 `#GP` 造成 exit 风暴

`VmExit/VmExitDispatcher.cpp:306-311`：对**可重复触发**的未知 reason 注入 `#GP`，guest 若反复触发同一 exit 就形成风暴，来宾无法推进 → 取不到时钟中断（与 0x101 同源）。另：`vmexit_unimplemented`（`VmExitException.cpp:3-7`）**从未被 switch 调用**，是死代码。

### D5【P1】`EXCEPTION_OR_NMI` 跳过 IDT-vectoring 重注入

`VmExit/VmExitDispatcher.cpp:258-261`：reason 为 `EXCEPTION_OR_NMI` 时不做重注入。被打断的投递事件可能永久丢失，需按 SDM 27.7.2 核实。

### D6【P1】MSR 语义

- `VmExit/VmExitMsr.cpp:131-136`：EFER 写入要求新值 **等于**当前值，否则 `#GP`——**严于硬件**（真实硬件允许合法位变更）。
- `:145、156-167`：MTRR 写入经 `wrmsr_safe` **落到宿主物理 MSR** → guest 可改宿主内存类型。

### D7【P1】MTF handler 持全局锁做重活

`VmExit/VmExitException.cpp:140` 持 `eptWatchList_lock`，`:156-194` 在锁内做 4KB guest 读（`read_guest_virtual_memory`）+ `invept_single_context`。且 `:142` 只判 `ID == -1` **不判上界**就索引 `eptWatchList[ID]`。

### D8【P1】`SafeVmCall` / `SafeVmCallEx` 吞掉一切异常

`DbgkSysWin11/Hvm/HypervisorGatewayBroadcastSupport.cpp:21-31、46-62`：`__try/__except(EXCEPTION_EXECUTE_HANDLER)` 把「非 VMX 上下文的 VMCALL 触发 #UD」这类**配置错误**当成普通失败，掩盖问题。

### D9 已核对为「设计如此」

- **MOV FROM CR0/CR4 不产生 VM-exit**（SDM 25.1.3：mask 非零时读走 Read Shadow，仅写 host-owned 位才 exit）→ `vmexit_cr_handler` 只实现 CR3 读（`VmExitControl.cpp:234-247`）**正确**。
- 异常位图全 0（`VmcsControls.cpp:216-234`）不漏功能所需异常：`#BP/#DB/#PF/#UD` 交 guest 原生处理，INT3 隐藏靠 EPT fake page，VMM 主动异常走 VM-entry 注入。
- **`vm-exit.asm` 正确**：448B 栈 ≥ `guest_context` 440B；`and rsp,~0xF` + `sub 512` + `sub 20h` 使进入 C++ 时 `RSP ≡ 8 mod 16`，符合 Win64 ABI；vmresume 失败路径先 pop 再写 `$rsp`（`:177-185`）；`vmxoff; jbe` 判失败正确。
- `recover_nmi_blocking` 的 IDT-vectoring valid 守卫（`VmExitDispatcher.cpp:89-95`）与 SDM / KVM `vmx_recover_nmi_blocking` 一致；VMfail 判定（`:144-145`）正确；`record_vmresume_failure` 单核无锁写快照正确。

## E 同步原语与锁序

### E1【P0】自旋锁实现

`Sync/spinlock.cpp:23-56`：朴素退避锁。缺失项（对照 `KeAcquireSpinLock` 语义）：

- **不提 IRQL**（`KeAcquireSpinLock` 会提到 DISPATCH_LEVEL）；
- 无 owner、无递归检测、无超时、无死锁诊断；
- `unlock` 是裸写 `*lock_ = 0`，**无释放屏障**（`KeReleaseSpinLock` 隐含 `KeMemoryBarrier`）。

注：不抬 IRQL 这一点在「调用点已在 VM-exit（IF=0）」的前提下是**成立**的——hvpp 的 `lib/spinlock.h` 同样是纯 `atomic_flag` + `pause` 退避锁，其 README 明说「VM-exit handler 中中断已关、IRQL 实际等同 HIGH_LEVEL」。**问题不在锁本身，而在它被用在了不是 VM-exit 的上下文**（见 E2）。

### E2【P0】锁 + IPI 广播的组合 → 0x101

完整偏序（已逐点核对，**无反向获取、无 ABBA**）：

```
eptWatchTransaction_lock
   ├─→ g_TrackerLock            (EptWatchActivation.cpp:27→49; EptWatchDeactivate.cpp:116→290)
   │      └─→ eptWatchList_lock (Cr3Tracker.cpp:57→72)
   ├─→ eptWatchList_lock        (Activation:27→59; Deactivate:116→117; Install:47→68)
   ├─→ hooked_page_list_lock / functions_lock / pool locks
   └─ 叶子：g_vmx_init_lock、vmcs_dump_lock
pool: lock_for_request_allocation → lock_for_reading_pool (PoolAllocation.cpp:144→68)
```

`eptWatchList_lock` 之下不再取任何锁（所有 `Cr3TrackerRelease` 都在 unlock 之后：`Activation:64-65/78-79`、`Deactivate:289-290`）；`hooked_page_list_lock` 与 `functions_lock` 互不嵌套（`EptCommon.cpp:83/193`）。

**真实风险不是锁序，而是「锁内长操作 + IPI_LEVEL + IF=0」**：

- `HypervisorRoutines/HypervisorVmcsDump.cpp:12-213`：`vmcs_dump_lock` 内约 **150 次** `LogDump`（VMREAD + DbgPrint），入口在 `VmcallDispatch.cpp:377`。
- `EptWatchActivation.cpp:27-134` / `EptWatchBreakpointInstall.cpp:47-188`：事务锁内整页 guest 读 + split + 池分配 + 逐核 commit。
- `KeGenericCallDpc` 在 IPI_LEVEL 设屏障等全部核（`Common/Ring0/Hvm/ntapi.h:15-17`）。

→ 见 `docs/08` R1/R2/R3 的完整推导。

### E3【P1】`wait_for_page_quiescence` / `wait_for_function_quiescence` 无上限

`Ept/EptCommon.cpp:301-329`：`while(...) _mm_pause();`，无超时、无让步，且在**持有事务锁**时被调用（`EptWatchDeactivate.cpp:74`、`EptHookCleanup.cpp:59/114/164/188`）。死锁构造见 `docs/08` R2。

对照：DdiMon 卸载 hook 用 `UtilForEachProcessor` **逐核同步下发**，源码里**没有引用计数、也没有「等所有核退出 hook」的保护**（README 自认 "not robust"）；HyperPlatform 靠 per-core EPT 天然无跨核引用；HyperDbg 把广播责任显式交给调用者。**主流不等待**——用「同步逐核执行 + 事后释放」，UAF 风险由调用方契约承担。

### E4【P1】遥测跨核读无同步

`VmExit/VmExitTelemetry.cpp:13-41`：`vmexit_telemetry` 由本核写、他核读（dump 路径），无屏障/无原子。

## F 生命周期、资源与释放策略

### F1【P0】卸载竞态直接蓝屏

- `Driver/DriverLifecycle.cpp:61-67`：`AreAllVcpusLaunched()` 为假即 fatal。
- `Common/Ring0/Hvm/VmmReleasePolicy.h:26-33`：`CanRelease` 除 `allVcpusQuiescent` 外**额外要求 `lifecycle ∉ {running, stopping}`**。
- `Vmm/VmmContext.cpp:37-49` 同理。

即：卸载流程只要与运行期状态有交集，就是 `KeBugCheckEx` 而不是「拒绝卸载 + 返回错误」。**用户态调用者无法优雅处理**。

### F2【P1】`Driver/DriverInitOffset.cpp:133` 的 `KeDelayExecutionThread`

存在一个延迟日志线程（`InitOffsetLogThread`），用 `KeDelayExecutionThread` 轮询 `g_InitOffsetLogPending`。属初始化期辅助路径，风险可控，但需确认它不会在 VMX 已接管后仍在跑（否则在根态竞争）。

### F3【P1】`Unload` 无条件 `disable_vmx_operation()`

`Driver/DriverLifecycle.cpp:93`：无论当前是否仍在 VMX 中，都无条件关闭。需确认与 `CanRelease` 的判定顺序。

### F4【P1】`outFile` 在根态做文件 IO

`Driver/Driver.h:36` + `Driver/VtLoadLog.cpp:189-238`：门闸只有 `KeGetCurrentIrql() != PASSIVE_LEVEL`。而 **VM-exit 不改变 IRQL**——guest 在 PASSIVE 发 VMCALL，根态仍是 PASSIVE → 门闸放行 → 在 **VMX 私有宿主栈**上 `ZwCreateFile` / `ZwWriteFile`。

对照 hvpp README：「VM-exit handler 中中断已关、IRQL 等同 HIGH_LEVEL」，文件 IO 需要 PASSIVE/≤APC_LEVEL，**语义直接冲突**。

（`sLog` 被 `_SERIAL_DEBUG_LOG` 关闭，展开为空宏，串口路径目前安全。）

## H 与开源实现横向对照

### H0 重要前提修正

**`tandasat/HyperPlatform` master 并不实现 EPT hook / MTF**。其 `ept.h` 只导出 7 个 API（`EptIsEptAvailable` / `EptGetEptPointer` / `EptInitializeMtrrEntries` / `EptInitialization` / `EptTermination` / `EptHandleEptViolation` / `EptGetEptPtEntry`）。EPT hook + MTF 的参考实现在 **`tandasat/DdiMon`**（`shadow_hook.cpp`）。**评审时不能把两者的能力混为一谈。**

### H1 EPT 数据组织

- HyperPlatform：`EptData` 注释 `// EPT related data stored in ProcessorData`，每核独立 `ept_pml4` + 预分配条目，**无锁**，仅 `InterlockedIncrement`；跨核共享的只有 `SharedProcessorData`（MSR/IO bitmap），用 `reference_count` 管理。
- HyperDbg：注释 "Each core needs its own splitting page-tables"；改 PML1 时用自旋锁保护区（`Ept.c:1181` 的 `EptSetPML1AndInvalidateTLB`）。
- KVM：EPT 属 VM、多 vCPU 共享 → 必须远端刷新。

**通行做法**：per-vCPU / per-processor 独立 + 无锁或极短锁；只有共享时才加同步。

### H2 VM-exit 路径能否持锁 / 长操作

- hvpp README：*"you should think twice before calling any kernel function from VM-exit handler… in VM-exit handler, interrupts are disabled and your IRQL is effectively HIGH_LEVEL"*。
- HyperPlatform 热路径**不分配池内存**，耗尽直接 `HYPERPLATFORM_COMMON_BUG_CHECK`；分配只在 `PAGED_CODE()` 初始化路径。
- KVM 把 TLB 刷新延后到 `vcpu_enter_guest` 处理 `KVM_REQ_TLB_FLUSH`，**不在 exit handler 内等**。

**通行做法**：VM-exit 内只做定长、无分配、无阻塞操作；持锁范围限于单条表项更新。

### H3 unhook 是否等待其它处理器

主流**不等待**：DdiMon 用 `UtilForEachProcessor` 逐核同步下发还原；HyperPlatform 靠 per-core EPT 天然无跨核引用；HyperDbg 把广播责任交给调用者。UAF 风险由调用方契约承担（DdiMon 的 README 自认 "not robust, production quality software"——**这是公认的脆弱点，不是优点**）。

### H4 MTF

SDM Vol3C §25.5.2：MTF 是 VM-execution control，置 1 后在「第一条指令之后」产生 MTF VM-exit；**MTF VM-exit 优先于 debug-trap 异常**；pending MTF 可经 VM-entry 注入（§26.5.2）。它与 guest 的 `RFLAGS.TF` / `DR7` 单步**相互独立、guest 不可见**。

DdiMon 配对：`ShpEnablePageShadowingForRW` → `ShpSetMonitorTrapFlag(true)` → `ShpSaveLastHookInfo`；恢复端 `ShpRestoreLastHookInfo` → 切回 exec 影子页 → 清 MTF，用 `NT_ASSERT` 防重入。

**通行做法**：置 MTF 与登记恢复点必须**同一 handler 内、顺序紧邻、先改表项后置 MTF**，恢复路径幂等。→ 对应 D1。

### H5 INVEPT 作用域与刷新

SDM：**INVEPT 只作用于执行它的逻辑处理器**。共享 EPT 必须「一核改 + 逐核刷新」；per-core EPT 才可只刷本核。

本项目走的是「共享控制面 + 每核 EPT + 单核改表 + 全核逐核 INVEPT」，**结论是正确且自洽的**（见 §11）。

### H6 `KeIpiGenericCall` / `KeGenericCallDpc` 的权威语义

微软文档原文：*"causes the specified routine to run on all processors simultaneously"*、*"raises the IRQL to IPI_LEVEL… Each processor spins on a barrier until all processors have reached the barrier… KeIpiGenericCall waits for all calls to complete before returning"*。回调约束（`KIPI_BROADCAST_WORKER`）：*"run at IRQL = IPI_LEVEL, which is greater than DIRQL for every device"*，且 *"must satisfy the same restrictions as bug check callback routines"*（不能等待、不能访问分页内存、不能调用要求低 IRQL 的例程）。

IPI_LEVEL(14) 高于 CLOCK_LEVEL(13) → 广播例程久留即 **0x101**。**这就是「广播例程必须极短」的权威依据。**

### H7 VMX / VM-entry 失败处理

- HyperPlatform：VMLAUNCH 失败 → 记日志 + Debug 断点 + 清理返回，**不蓝屏**；仅 VMRESUME/VMXOFF 这类宿主侧不可恢复失败才 bugcheck。
- 审计实践（`VMXHypervisorToolbox` 的 `intel-vmx-code-audit.md`）：VM-Entry Failure（exit reason bit31）必须检测并清标志；EPT misconfig 应「记录完整 EPT 状态并尝试恢复」而非直接 shutdown。

**通行做法**：初始化 / guest-state 类失败 = 记录 + 回滚 + 不蓝屏；宿主侧 VMX 指令失败 = fail-fast。→ 对应 D2。

### H8 CPU 代际差异

- 控制位统一收敛：`(期望 | Low) & High`，取自 `IA32_VMX_*_CTLS`（SDM §24.6.1）。
- CR0/CR4 固定位：`mask = FIXED0 ^ FIXED1`（SDM §26.3.1.1）。
- 能力位分叉：INVEPT 类型由 `IA32_VMX_EPT_VPID_CAP` 报告；KVM 用 `cpu_has_vmx_*` 回退。

**通行做法**：能力位驱动的「统一收敛 + 局部回退」，不按型号硬编码分叉。→ 本项目 G1 符合。
