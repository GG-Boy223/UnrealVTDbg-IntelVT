# 12 最终结论

**任务**：自建 Intel VT-x 调试器，排查 `0x101 CLOCK_WATCHDOG_TIMEOUT`；不使用锁；不做无意义的边界判断；审阅 main 全部历史节点；以官方文档与开源 VT 实现为依据。

**范围**：VT_Driver（187 文件 / 21418 行）、DbgkSysWin10|11（Hvm 各 9 文件）、Common/Ring0/Hvm（12 文件）、Common/Ring0/Spinlock、Hook/vmx、全部 ASM。

**本文是最终结论**，汇总并取代 `docs/08`（首轮 0x101）、`docs/09`（多维度审计，含结论修正）、`docs/10`（0x101 全通路）、`docs/11`（历史锁演进与必要性）。

## 一 一句话结论

> **0x101 不是「中断被吞」，而是「处理器回不到来宾」。**
>
> 根因是**数据模型与同步模型错配**：EPT 是**每核独立**的（正确），同步却按**全局共享资源**设计（错误）。由此产生的 **全局事务锁 + IPI 全核广播**，让所有逻辑处理器在**时钟中断被双重屏蔽**（`IPI_LEVEL` + 根态 `IF=0`）的状态下，串行排队等同一把锁。
>
> **本项目并不需要这套锁体系。11 项同步机制可收敛到 2 项，收敛后 0x101 的 4 条主通路一并消失。**

## 二 0x101 判据（本轮把前提钉死了）

### 2.1 时钟中断不经 VMM

`Vmcs/VmcsControls.cpp:241`：`pinbased_controls.external_interrupt_exiting = false`。  
全仓库 `external_interrupt_exiting` **仅此一处赋值**，运行期**从不打开**。

→ APIC 定时器的时钟中断是物理中断，**直接投递给来宾**，不产生 VM-exit、不经 VMM 注入。

→ 因此：**0x101 不是「中断被 VMM 吞了」，只能是「该处理器没能回到来宾执行时钟 ISR」。**

### 2.2 三条必要条件（外加一条 IRQL 的）

| 条件     | 含义                                                                 |
| ------ | ------------------------------------------------------------------ |
| **C1** | 处理器长时间停在 VMX root（`IF=0`），压根回不到来宾                                  |
| **C2** | 处理器在 root 态无限自旋（C1 的极端：永远回不去）                                      |
| **C3** | 处理器在 root/guest 间高频往返，但**来宾零前进**，永远碰不到可投递中断的指令边界                   |
| **C4** | 处理器停在 **`IPI_LEVEL`**（`CLOCK_LEVEL=13 < IPI_LEVEL=14`，时钟被 IRQL 屏蔽） |

### 2.3 已排除的三条常见误判（各有依据）

| 曾被怀疑                                               | 结论     | 依据                                                                                            |
| -------------------------------------------------- | ------ | --------------------------------------------------------------------------------------------- |
| 时钟中断被 VMM 拦截后丢失                                    | **排除** | `external_interrupt_exiting = false` 且运行期从不打开                                                 |
| VMM 把来宾 `IF` 清 0                                   | **排除** | `GUEST_RFLAGS` 在 VM-exit 路径**只有读**（`VmExitDispatcher.cpp:207` 等），唯一一次写在初始化 `VmcsGuest.cpp:79` |
| `recover_nmi_blocking` 置 `blocking_by_nmi` 导致中断被阻塞 | **排除** | `blocking_by_nmi` 只阻塞 **NMI/SMI**，不阻塞可屏蔽中断；时钟中断是可屏蔽中断                                         |

### 3.1 两条最需要理解的通路

**P9（频率最高）**：`KeGenericCallDpc` 是 `KeIpiGenericCall` 的底层实现，按微软文档在 **`IPI_LEVEL`** 运行回调并**设屏障等全部处理器到达**，回调约束「等同 bug-check 回调」。本项目在回调里发 VMCALL 进根态（`IF=0`）并抢全局事务锁 → 该核同时处于 **`IPI_LEVEL`（屏蔽时钟）+ `IF=0`（屏蔽一切）** 双重屏蔽。**每次下断点都走这条路径。**

**P8（最隐蔽，但非小概率）**：

```
CPU A：持事务锁 → ept_watch_deactivate_internal(CPU B 的页) → 自旋等 B 的 mtf_reference_count 归零
CPU B：有 pending MTF 未清，且下一条指令恰为 VMCALL（Dbgk 高频行为）
       → VM-exit reason = VMCALL → 抢同一把事务锁 → 自旋等 A 放锁
```

**A 等 B 清 MTF，B 等 A 放锁 → 双核同时 0x101。** 而 `mtf_reference_count` 的唯一递减点要靠 B 回到来宾才能触发——B 恰恰回不去。  
放大因素：`Common/Ring0/Hvm/VmcallDispatchPolicy.h:9-15` 的 `IsEptMutation()` **漏收** `VMCALL_EPT_RIP_HOOK` / `READ_SOFTWARE_BREAKPOINT` / `READ_EPT_FAKE_PAGE_MEMORY`，而这三条都会抢事务锁 → `broadcast_hook_function` 是**每核都真发 VMCALL**，「每核同时抢锁」在这条路径上是**必然**。

**P10（解释了一个怪现象）**：`VmExitEpt.cpp:174-182` 的限次保护**只对「连续相同 GPA + qualification」计数**，GPA 一交替就重置为 1 → 永远到不了 64 次 → 无限 root↔guest 往返 → 来宾零前进 → 0x101。  
→ **同一缺陷有时报 `0x20001`、有时报 `0x101`，差别只在 GPA 是否交替。**

## 四 锁与事务：本项目是否真的需要

### 4.1 历史事实（main 全 26 节点）

用 `git log -S` 追溯 11 项同步机制的引入节点：

| 机制                                                                                                                         | 引入节点        |
| -------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `vmcs_dump_lock`、`eptWatchList_lock`、池锁、`KeGenericCallDpc` 广播                                                              | a9ef865     |
| `g_TrackerLock`                                                                                                            | ba4c0d1     |
| **`eptWatchTransaction_lock` + `mtf_reference_count` + 忙等**                                                                | **ffd837b** |
| `hot_reference_count` + `wait_for_page_quiescence`/`wait_for_function_quiescence`、`hooked_page_list_lock`、`functions_lock` | 9ddfe75     |
| **`g_vmx_init_lock`**                                                                                                      | **76b7072** |
| 广播侧事务模式（`KeSignalCallDpcSynchronize` 选举属主）                                                                                 | cb1197e     |

**26 个节点中 7 个新增了锁，而没有任何一个节点删除过任何一把锁。**

`81660d0`（"将普通 watch 重操作移出全局表锁"）的实际 diff 是：

```diff
-  spinlock::lock(&eptWatchList_lock);
+  spinlock::lock(&eptWatchTransaction_lock);
```

**把重操作从表锁搬到了新引入的事务锁——「一把全局锁跨越跨核重操作」这个结构原封不动。** 提交说明里那句「VM-exit 热路径不会长时间自旋」只对表锁成立，对事务锁不成立。`5700be5` 是同一模式。  
→ **每次都在缩短一把锁的持有时间，从未质疑「为什么需要一把全局锁」。**

### 4.2 必要性判定

| 机制                                                 | 保护的状态            | 真的跨核共享？         | 判定                   |
| -------------------------------------------------- | ---------------- | --------------- | -------------------- |
| `g_vmx_init_lock`                                  | VMXON 初始化序列      | **否**           | **【完全不需要，应删除】**      |
| `eptWatchTransaction_lock`                         | Hook/Watch 事务    | **否**（EPT 每核独立） | **【不需要，应删除】**        |
| `KeGenericCallDpc` 广播 + 广播事务模式                     | 跨核执行 EPT 变更      | **否**           | **【不需要，应删除】**        |
| `vmcs_dump_lock`                                   | VMCS dump 输出     | 是（但只是调试输出）      | **【不需要，改本核缓冲】**      |
| `eptWatchList_lock`                                | 全局 256 项 watch 表 | 是，但**是设计选择的结果** | **【应降级为每核表】**        |
| `hooked_page_list_lock` / `functions_lock`         | 每核页表 / 每页函数链     | **否**（本就是私有）    | **【应改「谁拥有谁访问」】**     |
| `mtf_reference_count` / `hot_reference_count` + 忙等 | 记录存活期            | 是               | **【机制需要，忙等不需要】**     |
| 池管理器锁                                              | 全局池              | **是**           | **【锁需要，但不得在根态调用】**   |
| `g_TrackerLock`                                    | 128 槽 Cr3Tracker | 是               | **【锁需要，但取决于功能是否保留】** |

### 4.3 证据最硬的一条：`g_vmx_init_lock` 完全不需要

`76b7072` 的理由是「P0-003：多核 VMX 初始化自旋锁，防止**并发** VMXON 竞态条件」。但：

- `initalize_vcpu` 全仓库**只有一个调用点**：`Vmm/VmmEntry.cpp:41`；
- 该调用点位于**顺序 `for` 循环**内，每轮用 `KeSetSystemGroupAffinityThread` 把**同一个线程**绑到目标核（`VmmEntry.cpp:38`），执行完再 `KeRevertToUserGroupAffinityThread`（`:59`）；
- 全仓库**没有任何** `KeGenericCallDpc` / `KeIpiGenericCall` 调用初始化路径。

→ **不存在并发，这把锁保护的是一个不存在的竞态。**  
（同一提交的说明里还写着「删除无意义的边界检查」——作者已有该自觉，只是没把同一标准用到锁上。）

### 4.4 真正需要的只有 2 类

| 类别           | 原因                                                                               | 约束                                      |
| ------------ | -------------------------------------------------------------------------------- | --------------------------------------- |
| **池管理器锁**    | 池是真正的全局共享资源                                                                      | **不得在 VMX root / VM-exit 中调用**（改为耗尽即失败） |
| **引用计数（机制）** | 跨核引用隔离，防 UAF，解决**真实问题**（`9ddfe75`：「修复 MTF *pending&#x20;*&#x671F;间卸载导致的 UAF 漏洞」） | **不得配合忙等**；改为不阻塞回收                      |

**收敛结论：11 项 → 2 项。**

## 六 需先确认（决定修复路线，二者必须二选一）

1. **跨核 EPT 操作走哪条路线？**
   - **(A) 「本核改本核 + 本核 INVEPT」** → 可删 `eptWatchTransaction_lock` + `KeGenericCallDpc` 广播 + 广播事务模式，0x101 主通路一并消失。**推荐。**
   - **(B) 保留「一核改全核 + 逐核 INVEPT」** → 则广播与逐核刷新必须保留（注意：`docs/08` §8 已证伪「只做本核 INVEPT」的说法，当前广播路径是**每个核都各自 INVEPT**，这是正确的）。
   - **两条路线不能混用**——混用正是当前模糊地带的来源。
2. **`Cr3Tracker` 是否保留？** 其 Observe 侧已实际不生效（`Cr3TrackerObserve` 全工程只剩 1 个调用点 `VmExitEpt.cpp:120`；CR3-load exit 路径不调用它；`Cr3TrackerWorker.cpp` 的 `TryConsumeCandidate` 无任何调用者）。这决定 `g_TrackerLock` 与整块代码的处置。
3. **实机 0x101 转储的 Arg3（PRCB）/ Arg4（挂起处理器索引）**：**多核同时挂起 → 直接坐实 P9**（修复应从 F11 入手）；**单核挂起 → 指向 P1/P2/P3/P4 这类单核长操作**（修复应从 F2/F3/F4 入手）。
4. **是否见过 `0x00020001`（Arg1=7）与 `0x101` 交替出现？** 若交替 → 坐实 P10。
5. **`mtf_reference_count` 是否存在未配对的递增（引用泄漏）？** 若有，P7/P8 从「需要条件」变为「必然」。建议逐点核对 `mark_pending_mtf_page` 的每次成功返回是否都有对应的 `clear_pending_mtf_metadata`。
6. **实机是否出现过 `FAST_FAIL_INCORRECT_STACK`？** 若有 → P3 优先级提到最高。
