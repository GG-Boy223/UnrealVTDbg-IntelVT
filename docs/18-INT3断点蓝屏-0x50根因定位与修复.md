# 18 — INT3 断点场景 0x50 蓝屏：根因定位与修复

> 转储：`F:\MiniDmp\091926-8500-01.dmp`
> 场景：**x64dbg 下 INT3 软件断点时蓝屏**
> 结论：**已定位到具体指令与具体函数，属本驱动缺陷，已修复。**
> 与 `docs/17` 的四个转储**不是同一台机器**，也不是同一类问题。

---

## 1. 一句话结论

崩溃发生在 **`DbgkSysWin10.sys`** 的 `Cr3Candidate.cpp` 里，
`HasExpectedPml4Layout()` 执行 `pml4[g_Baseline.selfIndex]` 时，
`pml4` 是 `MmGetVirtualForPhysical(被扫描的物理页帧)` 的返回值 ——
**该函数只是「物理内存窗口基址 + 物理地址」的纯加法，不做任何映射有效性校验**。
命中的物理页帧落在窗口空洞里 → 解引用触发**非分页区缺页** →
内存管理器直接 `KeBugCheckEx(0x50)`，**`__try/__except` 根本拦不住**（原保护是假的）。

即：这段代码在所有构建里完全一致 → **本地 PDB 可以放心使用**。

## 4. 完整调用链（栈还原 + 源码双向确认）

从崩溃栈上还原（`dps` + 帧算术校验）：

```
DbgkSysWin10!HandlerDispatchRoutin+0xae        ← IOCTL 分发
 └ DbgkSysWin10!DispatchBreakpointIoctl+0xcf    ← 断点 IOCTL
    └ DbgkSysWin10!RemoveSoftwareBreakpoint+0x71   ← 移除 INT3 软件断点
       └ DbgkSysWin10!DeleteSoftwareBreakpoint+0x24
          └ DbgkSysWin10!CaptureProcessCr3+0x4a          ← 抓目标进程 CR3
             └ DbgkSysWin10!Cr3ResolveProcess+0x275      ← 逐级降级解析
                └ DbgkSysWin10!Cr3ScanPhysicalMemory+0xab  ← 全物理内存逐页扫描
                   └ DbgkSysWin10!`anonymous namespace'::HasExpectedPml4Layout+0x24  ★ 崩溃
```

**校验说明**：`TryCandidate+0x25` 那格虽然也落在本驱动范围内，但它**不是返回地址**
（`0x21029630` 位于 `e8 f1 01 00 00` 这条 `call` 指令的中间）。
真正的返回地址是 `Cr3ResolveProcess+0x275`，与源码第 254 行
`candidate = Cr3ScanPhysicalMemory(&probe, &scannedPages);` 精确对应。

源码侧逐环确认（`grep` 结果）：

| 调用 | 位置 |
|---|---|
| `CaptureProcessCr3` → `Cr3ResolveProcess` | `DebugBreakCore.cpp:61` |
| `DeleteSoftwareBreakpoint` → `CaptureProcessCr3` | `SoftwareBreakpoint.cpp:13/70/128` |
| `Cr3ResolveProcess` → `Cr3ScanPhysicalMemory` | `Cr3Resolver.cpp:254` |
| `Cr3ScanPhysicalMemory` → `HasExpectedPml4Layout` | `Cr3Candidate.cpp:252` |

`Cr3ResolveProcess` 的降级顺序（`Cr3Resolver.cpp:214-256`）：
缓存 → 调用方传入值 → `DirectoryTableBase` → 附加 CR3 → **全物理内存扫描（最后手段）**。
本次是前四级全部失败，才落到扫描。

## 5. 现场还原

### 5.1 陷阱帧（x64 `_KTRAP_FRAME`）

硬件异常帧落在 `ffff8601_0405edc8`：

| 偏移 | 地址 | 值 | 字段 |
|---|---|---|---|
| +0xF8 | `0405edc8` | `fffff804_21029730` | **Rip** = 出错指令 |
| +0x100 | `0405edd0` | `00000000_00000010` | SegCs |
| +0x108 | `0405edd8` | `00000000_00050202` | EFlags |
| +0x110 | `0405ede0` | `ffff8601_0405edf0` | Rsp |
| +0x118 | `0405ede8` | `00000000_00000018` | SegSs |

帧基址 = `0405edc8 - 0xF8 = 0405ecd0`，与出错时 `rsp = 0405edf0`（= 帧基址 + 0x120）自洽。
**注**：`Rax/Rcx/Rdx` 等通用寄存器字段在本转储里已被清零（bugcheck 路径复用了同一栈），
因此改用下面的方法还原关键输入。

### 5.2 被扫描的物理页帧

`HasExpectedPml4Layout` 的序言 `mov [rsp+8],rbx` 把调用方 `rbx` 存进了调用者的影子空间：

```
[0405ee18] = fffff804`2102956b   ← 返回地址 = Cr3ScanPhysicalMemory+0xab  ✓
[0405ee20] = 00000000`003bd000   ← 保存的 rbx = Cr3ScanPhysicalMemory 的循环变量 candidate
```

`Cr3ScanPhysicalMemory` 的 `rbx` 就是 `candidate`（`add rbx,1000h` 逐页递增）。
**所以 `candidate = 0x3BD000`**（物理 3.9 MB 处的一页）。

### 5.3 `selfIndex` 与物理窗口基址（推导，附自洽校验）

出错时 `EA = pml4 + selfIndex*8 = 0xFFFFCF8F7C9FBE48`，且
`pml4 = MmPhysicalMemoryBase + candidate`。

`MmPhysicalMemoryBase` 必然页对齐，因此：
`(0xFFFFCF8F7C9FBE48 − selfIndex*8 − 0x3BD000) mod 0x1000 = 0`
→ `selfIndex ≡ 0x1C9 (mod 0x200)`，在 `[0,511]` 内**唯一解 `selfIndex = 457 (0x1C9)`**
→ `MmPhysicalMemoryBase = 0xFFFFCF8F7C63E000`，`pml4 = 0xFFFFCF8F7C9FB000`。

**这个推导同时是一个强自洽校验**：
`selfIndex = 457` 落在合法区间 `[0,511]` 内 → 与 §6.1 的论证一致（索引不可能是元凶）。
若按 Windows 默认自映射索引 `495 (0x1ED)` 代入，得到的基址**不是页对齐的**，自相矛盾。
`457` 是随机化内核布局下的正常取值。

**关键推论**：读偏移 `457*8 = 0xE48 < 0x1000`，即**读落在与 `pml4` 同一个 4KB 页内**。
所以不是"跨页读越界"，而是**整页（物理 `0x3BD000`）根本不在物理内存窗口里**。

## 6. 根因分析

### 6.1 先排除「索引越界」这个直觉答案

`g_Baseline.selfIndex` 由 `InitializeBaseline()` 写入（`Cr3Candidate.cpp:54-76`）：

```cpp
ULONG selfIndex = MAXULONG;
for (ULONG index = 0; index < 512; ++index) {
    if ((pml4[index] & kEntryAddressMask) == currentCr3) { selfIndex = index; break; }
}
...
if (selfIndex == MAXULONG || kernelEntry == 0) { return FALSE; }   // 失败路径不写全局
g_Baseline.selfIndex = selfIndex;                                   // 只在成功路径写
```

- 索引被循环**硬性限定在 `[0,511]`**；
- 失败路径在写全局之前就 `return FALSE`，不会留下半初始化状态；
- `EnsureBaseline()` 的发布顺序是「先写字段 → 再置 `state=2`」，
  x86 TSO 下观察到 `state==2` 必然也能观察到字段（x86 商店顺序保证）。

→ **`selfIndex` 只可能是合法值。元凶只能是 `pml4` 本身。**

（§5.3 的推导结果 `457 ∈ [0,511]` 与此完全一致。）

### 6.2 真正的根因：`MmGetVirtualForPhysical` 不校验映射

```cpp
// Cr3Candidate.cpp:249-252（修复前）
PHYSICAL_ADDRESS address = { 0 };
address.QuadPart = candidate;
PULONG64 pml4 = static_cast<PULONG64>(MmGetVirtualForPhysical(address));
if (HasExpectedPml4Layout(pml4, candidate) && ValidateImage(candidate, probe))
```

而 `candidate` 来自 `MmGetPhysicalMemoryRanges()` 报出的区间逐页枚举。

`MmGetVirtualForPhysical` 的语义是**纯偏移映射**（物理内存窗口基址 + 物理地址），
它**不检查**该物理页是否真实存在、是否已映射进窗口。
而 `MmGetPhysicalMemoryRanges()` 报出的区间**并不保证每一页都落在窗口内** ——
窗口里存在空洞（固件保留区、非 RAM 区间等）。

于是：**扫描到一个落在空洞里的页帧 → 解引用 → 非分页区缺页 → 直接蓝屏。**

### 6.3 为什么 `__try/__except` 没救回来（关键）

原函数包了 `__try/__except (EXCEPTION_EXECUTE_HANDLER)`，看起来是安全的。**但它是假的。**

非分页区缺页（`PAGE_FAULT_IN_NONPAGED_AREA`）由内存管理器**直接调用 `KeBugCheckEx`** 上报，
**不会**被转换成可分发的异常。SEH 能接住的只有「可分页区域缺页（可换入）」或
「访问违例」这类可继续的异常。因此：

> **在非分页地址上解引用，`__try/__except` 提供零保护。**

这一点在本转储里得到直接印证：函数里明明有 `__except`，结果仍然是 0x50 蓝屏。

### 6.4 同文件内已有正确姿势 —— 这是疏漏，不是设计

| 函数 | 读取方式 |
|---|---|
| `TranslateVirtualAddress` | `ReadPhysical` ✅ |
| `ValidateImage` | `ReadPhysical` ✅ |
| `Cr3ValidateCandidate` | `ReadPhysical` ✅ |
| **`HasExpectedPml4Layout`** | **裸虚拟解引用** ❌ |

**整个文件里只有这一个函数用了裸解引用。** 而 `Cr3ValidateCandidate`
（第 203-204 行）做的是**完全相同的事**（校验 selfEntry / kernelEntry 与基线一致），
却全程走 `ReadPhysical`。

→ 结论明确：这是**疏漏**，修复方向就是把它对齐到同文件的既有安全姿势。

### 6.5 为什么"以前不崩，现在崩"

`Cr3ScanPhysicalMemory` 是**最后手段**，只有前四级解析全部失败才会执行。
本次是「移除 INT3 软件断点」路径需要目标进程 CR3，
缓存 / 传入值 / `DirectoryTableBase` / 附加 CR3 全部未通过校验，
于是落到全物理内存扫描 —— 一旦扫到空洞页帧，必崩。

**触发条件具备确定性**：只要走到扫描路径，且物理内存区间里存在窗口空洞，就会命中。
不是偶发竞争，是**必然**。

## 7. 修复

### 7.1 改动内容

`DbgkSysWin10/Cr3/Cr3Candidate.cpp` 与 `DbgkSysWin11/Cr3/Cr3Candidate.cpp`（两份同构，同步修复）：

**（1）`HasExpectedPml4Layout` 改为按物理地址读**

```cpp
// 修复后
BOOLEAN HasExpectedPml4Layout(
    unsigned __int64 candidateCr3)
{
    if (candidateCr3 == 0 || !EnsureBaseline())
    {
        return FALSE;
    }

    unsigned __int64 selfEntry = 0;
    if (!ReadPhysical(candidateCr3 + g_Baseline.selfIndex * sizeof(ULONG64), &selfEntry, sizeof(selfEntry)) ||
        (selfEntry & kPresentBit) == 0 ||
        (selfEntry & kEntryAddressMask) != candidateCr3)
    {
        return FALSE;
    }

    unsigned __int64 kernelEntry = 0;
    if (!ReadPhysical(candidateCr3 + g_Baseline.kernelIndex * sizeof(ULONG64), &kernelEntry, sizeof(kernelEntry)))
    {
        return FALSE;
    }

    return (kernelEntry & kPresentBit) != 0 &&
        (kernelEntry & kEntryAddressMask) == g_Baseline.kernelEntryAddress;
}
```

**（2）调用点不再取虚拟地址**

```cpp
// 修复前
PHYSICAL_ADDRESS address = { 0 };
address.QuadPart = candidate;
PULONG64 pml4 = static_cast<PULONG64>(MmGetVirtualForPhysical(address));
if (HasExpectedPml4Layout(pml4, candidate) && ValidateImage(candidate, probe))

// 修复后
if (HasExpectedPml4Layout(candidate) && ValidateImage(candidate, probe))
```

### 7.2 依据

| 依据 | 说明 |
|---|---|
| **Intel/Windows 语义** | `MmGetVirtualForPhysical` 是纯偏移映射，不校验映射有效性 |
| **同文件既有模式** | `Cr3ValidateCandidate` 对同样的校验用 `ReadPhysical` |
| **转储实证** | 出错指令 = `pml4[g_Baseline.selfIndex]`；`candidate = 0x3BD000`；`selfIndex = 457` 合法 |
| **异常语义** | 非分页区缺页直接 bugcheck，SEH 无效 |
| **`ReadPhysical` 语义** | `MmCopyMemory(MM_COPY_MEMORY_PHYSICAL)` 先校验 PFN 再拷贝，非法地址返回失败状态 |

### 7.3 修复效果

- 空洞页帧从「**必然蓝屏**」变为「**返回 FALSE，跳过该候选**」，扫描继续。
- 语义等价：`selfEntry` 先判 present 与相等，不通过就不再读 `kernelEntry`，
  与原 `&&` 短路顺序一致（且少一次物理读）。
- 未新增任何边界判断、未引入锁。

### 7.4 顺带确认：`InitializeBaseline` 不需要改

它也调用 `MmGetVirtualForPhysical`（第 48 行），但传入的是
`Cr3NormalizeCandidate(__readcr3())` —— **当前正在运行的 CR3**，
其 PML4 必然已映射。**这里没有缺陷，不动它**（避免无意义改动）。

## 8. 能力边界（转储拿不到什么）

- Mini Kernel Dump **只包含**：崩溃栈、出错代码页、模块列表、处理器上下文。
  **不包含**驱动的数据段（`.data` / 全局量）。
  - 直接读 `g_Baseline`（`DbgkSysWin10+0x1E390`）→ `????????`，不可用。
  - 读 `g_Cache`、池内存、物理内存窗口内容 → 全部不可用。
  - 因此 §5.3 的 `selfIndex` 是**推导**（带自洽校验），不是直接读取。
- 其他函数所在代码页未被采集，无法反汇编验证每一环（已改用源码确认）。
- `nt` 符号仍不匹配（`WRONG_SYMBOLS_X64_TIMESTAMP_290802-123343`），
  但本报告**不需要** nt 符号：出错模块是 `DbgkSysWin10`，其符号已由本地 PDB 正确解析。

## 10. 后续建议

1. **本次修复需在本机构建验证**（本环境无法编译：MSBuild 被安全策略拦截）。
   重点验证：`x64dbg` 反复下/删 INT3 断点，确认不再蓝屏。
2. **性能观察（非本次改动，供参考）**：
   `Cr3ScanPhysicalMemory` 是 O(物理内存/4KB) 的全量扫描，且每个候选页都要做一次
   `MmCopyMemory`。32–64 GB 机器上是数百万次迭代，在 IOCTL 上下文里是长时间停顿。
   本次修复不改变复杂度（反而单次略慢），但该路径是最后手段、命中率低。
   若后续发现响应迟滞，可考虑按「可能的 CR3 对齐特征」预筛（例如只扫描前若干 GB，
   或先用 `ReadPhysical` 读 8 字节做廉价预筛），**但这属于独立优化，不在本次缺陷范围内**。
3. **建议把 `Cr3ScanPhysicalMemory` 的 `scannedPages` 与失败原因打进日志**
   （源码第 259-262 行已有 `resolve failed ... scanned=%llu`），
   便于下次直接判断是否走到了扫描路径。
