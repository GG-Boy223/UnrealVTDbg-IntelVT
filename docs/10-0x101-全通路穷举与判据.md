# 10 0x101 CLOCK_WATCHDOG_TIMEOUT 全通路穷举

本文**只回答一个问题：本项目里有哪些代码路径会导致 0x101**。不讨论 LA57、CR4 掩码、DR 寄存器等与 0x101 无关的缺陷（那些记录在 `docs/09`，本文不再展开）。

前置文档：`docs/08`（首轮 0x101 分析）、`docs/09`（多维度审计，含结论修正）。

---

## 1 先把判据收窄（本轮新增的关键核查）

### 1.1 时钟中断不经 VMM —— 这决定了 0x101 的形态

**已核查**：`Vmcs/VmcsControls.cpp:241`

```cpp
pinbased_controls.external_interrupt_exiting = false; // 允许中断直接进入来宾
```

且全仓库 `external_interrupt_exiting` **只有这一处赋值**（另两处是结构体声明 `VmcsControls.h:95`、`vmcs.h:298`），**运行期从未被打开**。

推论：

> APIC 定时器的时钟中断是物理中断，`external_interrupt_exiting = false` 时它**直接投递给来宾**，不产生 VM-exit，也不经 VMM 注入。
>
> 因此 **0x101 不是「中断被 VMM 吞了」，而只能是「该处理器没能回到来宾执行时钟 ISR」**。

（附带说明：`VmcsControls.cpp:42` 的 `acknowledge_interrupt_on_exit = true` 只在开启外部中断退出时才有意义，当前配置下不参与。）

### 1.2 IF 不会被 VMM 改坏 —— 已排除

**已核查**：`GUEST_RFLAGS` 在整个 VM-exit 路径中**只有读**（`VmExitDispatcher.cpp:207`、`VmExitCommon.cpp:337`、`EptWatchEvents.cpp:269`、`EptWatchQuery.cpp:13`、`HypervisorVmcsDump.cpp:33`），**唯一一次写**在初始化 `VmcsGuest.cpp:79`。

→ 「VMM 把来宾 RFLAGS.IF 清成 0，导致时钟中断永远不被识别」这条通路**不存在**。

### 1.3 `blocking_by_nmi` 不是时钟中断的阻塞源 —— 已排除

**已核查**：`GUEST_INTERRUPTIBILITY_STATE` 的写入点共 4 处：
- `VmcsGuest.cpp:95`（初始化置 0）
- `VmExitDispatcher.cpp:119-126`（`recover_nmi_blocking` 置 `blocking_by_nmi = 1`）
- `VmExitCommon.cpp:328-331`（`skip_instruction` 清 `blocking_by_sti` / `blocking_by_mov_ss`）
- `Globals/VmxState.cpp:74`（整字段读写助手，无掩码问题）

按 SDM，`GUEST_INTERRUPTIBILITY_STATE.blocking_by_nmi`(bit3) 只阻塞 **NMI 与 SMI**，**不阻塞可屏蔽中断**。时钟中断是可屏蔽中断。

→ 「`recover_nmi_blocking` 把 NMI 永久阻塞」是真实存在的风险（若来宾之后不再执行 IRET），但**它不会造成 0x101**。这是容易被误判为 0x101 的项，故显式排除。

### 1.4 由此得出的判据

> **0x101 ⟺ 某个逻辑处理器，在时钟看门狗间隔内，一次都没有回到来宾执行时钟 ISR。**

满足该判据的必要条件只有三条：

| 条件 | 含义 |
| --- | --- |
| **C1** | 处理器长时间停在 VMX root（IF=0），压根回不到来宾 |
| **C2** | 处理器在 root 态无限自旋（C1 的极端：永远回不去） |
| **C3** | 处理器在 root/guest 之间高频往返，但**来宾零前进**，因此永远碰不到可投递中断的指令边界 |

外加一条与 root/guest 无关的：

| 条件 | 含义 |
| --- | --- |
| **C4** | 处理器停在 **IPI_LEVEL**（高于 CLOCK_LEVEL=13），时钟中断被 IRQL 屏蔽——即使不在 root 态 |

下文按 C1→C4 穷举全部通路。

## 2 全通路穷举

### 通路 P1（C1）根态长操作：全局事务锁内做重活

**代码**：`VmCall/VmcallDispatch.cpp:91 / 105 / 122 / 188 / 240 / 307` 六处获取全局 `eptWatchTransaction_lock`，锁内是：
- `Ept/Watch/EptWatchActivation.cpp:29-113`：按 `Size` 逐页循环，每页 `get_physical_address` → `Cr3TrackerAcquire` → 逐 CPU `ept_watch_activate_internal`（可能 `split_pml2` + `pool_manager::request_pool`）
- `Ept/Watch/EptWatchBreakpointInstall.cpp:49-151`：每页 guest 整页读（`read_guest_virtual_memory`）→ `hide_cc_breakpoint` → 逐 CPU `commit_hide_cc_breakpoint`
- `Ept/Hook/Cleanup/EptHookCleanup.cpp:17-143`：跳板安装、整页 `RtlCopyMemory`、`invept`

**触发**：任一 `VMCALL_WATCH_*` / `HIDE_SOFTWARE_BREAKPOINT` / `EPT_RIP_HOOK` / `EPT_UNHOOK_FUNCTION`。这些命令由 Dbgk 驱动在**每次下断点/删断点**时发起。

**量化**：耗时 ≈ `页数 × (整页 guest 读 + split + 池分配 + N核 commit)`。N=24 时，一次跨 64 页的 watch 安装，串行化后单核停留时间可达**数十毫秒级**；若同一时刻其它核也在抢这把锁，则**所有核**一起停在 root。

### 通路 P2（C1）`vmcs_dump_lock` 内约 150 次 DbgPrint —— **已证伪，下调为「多余锁」**

**原判断**：`HypervisorVmcsDump.cpp:12` 取锁、`:213` 释放，中间约 150 次 `LogDump`（VMREAD + `DbgPrintEx`），带调试器时持锁可达数百毫秒到秒级。

**核对后的事实（本轮更正）**：`LogDump` 在 `Common/Ring0/SymbolicAccess/Utils/Log.h:60` 的 `#else` 分支里展开为**空宏**，而 `DEBUG_WinSys` **全仓库从未定义**（只有 `Log.h:5` 一行被注释掉的 `//#define DEBUG_WinSys`；`VT_Driver.vcxproj` 只定义 `DEBUG;_DEBUG_LOG`）。

`dump_vmcs()` 当前实际只执行：
- **2 行**真正的 `DbgPrintEx`（`:14` 与 `:211` 的首尾分隔线，**不受宏控制**）
- **150 次 VMREAD**（微秒级）

→ **持锁时间本就极短，P2 不是有效的 0x101 通路。** 第 2 项仍值得删（它本来就是不必要的锁），但**不能作为 0x101 的修复理由**。

> 方法论提醒：`LogDump` / `LogError` / `LogDebug` / `LogInfo` / `outLog` 在 `DEBUG_WinSys` 未定义时**全部是空宏**；只有 `sLog`（`_SERIAL_DEBUG_LOG`，亦为空）与 `outFile`（`VtLoadWriteLog`，真实文件 IO）需要区分对待。**分析根态耗时前必须先确认宏是否生效**——这是本报告第一版出现高估的根因。

### 通路 P3（C1）根态文件 IO

**代码**：`Driver/Driver.h:36` `#define outFile(...) VtLoadWriteLog(__VA_ARGS__)`；`Driver/VtLoadLog.cpp:189-238` 门闸只有 `KeGetCurrentIrql() != PASSIVE_LEVEL`，随后 `ZwCreateFile` + `ZwWriteFile` + `ZwClose`。
**关键**：**VM-exit 不改变 IRQL**（见 `docs/08` §1.4）。来宾在 PASSIVE 发 VMCALL → 根态仍是 PASSIVE → **门闸放行** → 在 **VMX 私有宿主栈**上做同步文件 IO。
**量化**：`FILE_SYNCHRONOUS_IO_NONALERT` 的同步文件 IO 可能等待 IO 完成甚至触发分页 → 处理器在根态**阻塞**，时长不可控（毫秒~秒级，取决于磁盘/内存压力）。
**注**：`sLog` 被 `_SERIAL_DEBUG_LOG` 关闭（`Common/Ring0/Comms/SerialPort.h:31` 展开为空宏），串口路径目前安全；`outFile` 在 `Ept/Build/EptPageTables.cpp`（构建期与 cleanup）、`Driver/DriverLifecycle.cpp` 等处活跃。

### 通路 P4（C1）池耗尽时在根态同步分配内存

**代码**：`PoolManager/poolmanager.h:130-136`

```cpp
if (new_pool == true && address == nullptr)
{
    (void)request_allocation(size, 1, intention);
    (void)perform_allocation();          // → ExAllocatePool*（PoolAllocation.cpp:56/71/83）
    scan_for_pool();
}
```

**触发**：hook/watch 安装（split、跳板、`__ept_hooked_page_info`）都走 `request_pool(..., true, ...)`。池一旦耗尽，就在**根态**同步 `ExAllocatePool*`。
**量化**：非分页池分配在内存压力下可能等待；且这与作者自述约束（`Ept/Build/EptPageTables.cpp:659`「VM-exit 路径只做纯内存写入，不分配内存」）直接冲突。

### 通路 P5（C1）整页 guest 读的页表遍历

**代码**：`Globals/GuestMemory.cpp:128-168` 的 `read_guest_virtual_memory`：`while (bytes_read < size)` 逐页 `gva2hva`（四级页表遍历）+ `memcpy_safe`。
**调用点（持锁时）**：`Ept/Watch/EptWatchBreakpoints.cpp:163`（整页 `PAGE_SIZE`）、`VmExit/VmExitException.cpp:156`（**MTF handler 内，持 `eptWatchList_lock`**）。
**量化**：单页 4KB 通常可接受；但 `VmExitException.cpp:156` 在**全局锁内**做，会把「一次 MTF 收尾」变成「持锁做一次 4KB 页表遍历 + INVEPT」。

### 通路 P6（C2）`spinlock::lock()` 无上限自旋

**代码**：`Sync/spinlock.cpp:28-51`

```cpp
while (!try_lock(lock_))
{
    for (unsigned __int32 i = 0; i < wait; ++i) _mm_pause();
    if (wait * 2 > max_wait) wait = max_wait; else wait = wait * 2;
}
```

无 owner、无超时、无死锁检测、不提 IRQL、`unlock` 无释放屏障。
**后果**：只要持锁者出现「长操作 / 异常路径漏解锁 / 递归获取」，**所有**等锁的核都在根态无限自旋 → 全部触发 0x101（不是单核）。

### 通路 P7（C2）`wait_for_page_quiescence` / `wait_for_function_quiescence` 无上限

**代码**：`Ept/EptCommon.cpp:301-329`：`while (hot_reference_count != 0 || mtf_reference_count != 0) _mm_pause();`（另一个只等 `hot_reference_count`）。
**调用点（均在持有事务锁时）**：

| 位置 | 等什么 |
| --- | --- |
| `Ept/Watch/EptWatchDeactivate.cpp:74` | 其它核的 `hot_reference_count` + `mtf_reference_count` |
| `Ept/Hook/Cleanup/EptHookCleanup.cpp:59` | `hot_reference_count` |
| `Ept/Hook/Cleanup/EptHookCleanup.cpp:114` | `hot_reference_count` + `mtf_reference_count` |
| `Ept/Hook/Cleanup/EptHookCleanup.cpp:164 / 188` | 同上（批量卸载） |

**这是最危险的一条**：它在**持锁**状态下等待**其它处理器**。只要被等的核因为任何原因（见下）不能递减计数，等待方就永久停在根态并占着全局锁，把**所有**核一起拖死。

### 通路 P8（C2）P7 与事务锁构成互相等待（自持死锁）

构造（已在 `docs/08` §3.2 给出，此处补全为 0x101 语言）：

```
CPU A：处理 VMCALL_WATCH_DELETE / VMCALL_EPT_UNHOOK_FUNCTION
        ├─ 已持有 eptWatchTransaction_lock
        └─ ept_watch_deactivate_internal(CPU B 的页记录)
             ├─ 置 removing = 1
             └─ wait_for_page_quiescence → 自旋等 CPU B 的 mtf_reference_count 归零   ← 停在这

CPU B：此前在一次 EPT violation 里 mark_pending_mtf_page() 成功
        → page_to_change=该页, mtf_pending=true, mtf_reference_count=1
        MTF 尚未触发（要等下一次 VM-entry 之后）
        来宾下一条指令恰为 VMCALL（Dbgk 驱动高频行为）
        └─ VM-exit reason = VMCALL（不是 MTF）
             └─ VmcallDispatch::Execute → spinlock::lock(eptWatchTransaction_lock)   ← 停在这
```

**A 等 B 清 MTF，B 等 A 放锁。两者都在根态（IF=0）→ 双核同时 0x101。**
`mtf_reference_count` 的唯一递减点是 `Globals/MtfPendingState.cpp:19` 的 `clear_pending_mtf_metadata`，只被 MTF VM-exit（`VmExitException.cpp:124/135/144/196`）或显式清理调用——即**必须靠 B 回到来宾才能清**，而 B 恰恰回不去。

**放大因素（关键）**：`Common/Ring0/Hvm/VmcallDispatchPolicy.h:9-15` 的 `IsEptMutation()` **未收录** `VMCALL_EPT_RIP_HOOK`、`VMCALL_READ_SOFTWARE_BREAKPOINT`、`VMCALL_READ_EPT_FAKE_PAGE_MEMORY`，而这三条**都会抢事务锁**。因此 `broadcast_hook_function`（`HypervisorGatewayBroadcast.cpp:144-183`）是**每核都真发 VMCALL**——「每核同时抢事务锁」在这条路径上是**必然**，不是概率。

### 通路 P9（C4）`KeGenericCallDpc` 广播回调停在 IPI_LEVEL

**代码**：`Common/Ring0/Hvm/ntapi.h:15-17` 声明 `KeGenericCallDpc` / `KeSignalCallDpcSynchronize` / `KeSignalCallDpcDone`；`DbgkSysWin10/11/Hvm/HypervisorGatewayApi.cpp` 共 30+ 处调用。

**语义（微软文档原文）**：*"causes the specified routine to run on all processors simultaneously"*、*"raises the IRQL to **IPI_LEVEL**… Each processor **spins on a barrier** until all processors have reached the barrier… **waits for all calls to complete before returning**"*；回调约束 *"must satisfy the same restrictions as **bug check callback routines**"*。

**x64 IRQL 序**：`CLOCK_LEVEL = 13 < IPI_LEVEL = 14` → **在 IPI_LEVEL 上时钟中断被屏蔽**。

**本项目的组合**：广播回调里执行 `SafeVmCall(...)` → VMCALL → VM-exit → 根态 **IF=0**。于是该核同时处于 **IPI_LEVEL（屏蔽时钟）+ IF=0（屏蔽一切中断）** 的双重屏蔽下，并在其中抢全局事务锁（P1）。

**量化**：24 核全部处于 IPI_LEVEL，串行排队等一把锁；屏障还要求**全部核到达**。总耗时超过看门狗间隔即 0x101——**且是全核一起**。

### 通路 P10（C3）来宾零前进：EPT 权限未恢复的交替循环

**代码**：`VmExit/VmExitEpt.cpp:174-182`

```cpp
if (last_gpa == gpa && last_qual == qual) ++unhandled_ept_violation_count;
else                                       unhandled_ept_violation_count = 1;   // ← 计数被重置
```

限次保护（`:188` 的 64 次）只在「**连续相同** GPA + qualification」时生效。因此：

> 若来宾在**两个不同 GPA**（或两种 qualification）之间交替触发 EPT violation，计数每次都重置为 1，**永远到不了 64 次** → 无限 root↔guest 往返 → 来宾**零前进** → 永远碰不到可投递中断的指令边界 → **0x101**。

**能产生交替 violation 的具体来源**：
- `VmExit/VmExitEpt.cpp:60-63 / 72-75 / 86-89` 与 `Ept/Watch/EptWatchInt3Execute.cpp:70-73`：`mark_pending_mtf_page` 返回 `false` 时**直接返回，不 swap EPT entry** → 该页 `execute` 永远为 0，来宾每次都取指失败。若同页还有另一个 watch/INT3 目标地址，就形成两个 GPA 交替 → 计数重置 → **无限循环**。
- `Ept/Watch/EptWatchEvents.cpp:282` 的 `RestoreEptPageProperties` 与 `VmExitEpt.cpp` 的 `mark_pending_mtf_page` 分处**两个不同临界区**（见 `docs/09` D1），配对可失败，正是上述 `false` 的来源。

**注意**：若始终是**同一** GPA + qualification，则先撞到 64 次限次 → `vmx_fatal_error` → **0x20001**（不是 0x101）。所以这条通路的表现是「**要么 0x20001，要么 0x101，取决于 GPA 是否交替**」——这解释了同一缺陷为何在不同机器/场景下报不同蓝屏码。

### 通路 P11（C3）未处理 exit 的 `#GP` 风暴

**代码**：`VmExit/VmExitDispatcher.cpp:306-311`：未收录 reason 一律注入 `#GP`。
**后果**：若某指令/状态被持续拦截但未实现，来宾反复触发同一 exit。`#GP` 注入到来宾后，来宾的 `#GP` 处理路径若本身又触发被拦截的 exit，就形成「无有效前进」的循环 → 0x101。
**注**：`vmexit_unimplemented`（`VmExit/VmExitException.cpp:3-7`）**从未被 switch 调用**，是死代码，说明这条兜底路径的意图未落地。

### 通路 P12（C2）卸载/关停路径的跨核等待

**代码**：`HypervisorGateway/hypervisor_gateway.cpp:140-144` 的 `invept()` 用 `KeGenericCallDpc`；`hvgt::vmoff` 经 `broadcast_vmoff`（`HypervisorGatewayBroadcast.cpp:15-22`）广播 `VMCALL_VMXOFF`。
**后果**：卸载时若有任一核正处于 P1~P5 的长操作或 P6~P8 的自旋中，**广播屏障永远等不到它** → 发起方停在 IPI_LEVEL → 0x101。
**关联**：`Driver/DriverLifecycle.cpp:61-67`、`Common/Ring0/Hvm/VmmReleasePolicy.h:26-33` 的 fail-fast 会先把这种情况变成 `KeBugCheckEx`——所以实际表现可能是 0x20001 而非 0x101，取决于先后。

## 3 通路汇总与排序

| 通路 | 条件 | 单核/多核 | 触发难度 | 时长量级 | 主要位置 |
| --- | --- | --- | --- | --- | --- |
| **P9** 广播回调停在 IPI_LEVEL | C4 | **全核** | 低（每次 Hook 都走） | 锁串行总时长 | `HypervisorGatewayApi.cpp`、`HypervisorGatewayBroadcast.cpp`、`VmcallDispatch.cpp` |
| **P8** P7 与事务锁互相等待 | C2 | **双核起** | 中（需 pending MTF + 下条指令是 VMCALL） | 永久 | `EptCommon.cpp:301-329`、`EptWatchDeactivate.cpp:74`、`MtfPendingState.cpp:19` |
| **P1** 事务锁内重活 | C1 | 持锁核 + 等锁核 | 低（每次下断点） | 十毫秒~百毫秒 | `EptWatchActivation.cpp:29-113`、`EptWatchBreakpointInstall.cpp:49-151` |
| **P7** 无上限跨核忙等 | C2 | 等待核 + 被等核 | 中 | 永久 | `EptCommon.cpp:301-329` |
| ~~**P2** `dump_vmcs` 内 150 次 DbgPrint~~ **已证伪** | — | — | — | 微秒级 | `HypervisorVmcsDump.cpp`（`LogDump` 为空宏，见 §2 P2） |
| **P6** `spinlock` 无上限 | C2 | 全核 | 取决于持锁者 | 永久 | `Sync/spinlock.cpp:28-51` |
| **P3** 根态文件 IO | C1 | 单核 | 中 | 毫秒~秒 | `VtLoadLog.cpp:189-238` |
| **P10** 交替 GPA 零前进循环 | C3 | 单核 | 中 | 永久 | `VmExitEpt.cpp:174-182`、`60-63/72-75/86-89` |
| **P4** 池耗尽根态分配 | C1 | 单核 | 中（池耗尽后） | 毫秒级 | `poolmanager.h:130-136` |
| **P5** 持锁整页 guest 读 | C1 | 持锁核 | 中 | 毫秒级 | `VmExitException.cpp:156`、`EptWatchBreakpoints.cpp:163` |
| **P11** `#GP` 风暴 | C3 | 单核 | 高 | 永久 | `VmExitDispatcher.cpp:306-311` |
| **P12** 卸载路径跨核等待 | C2 | 全核 | 高 | 永久 | `hypervisor_gateway.cpp:140-144` |

**最重要的两点**：
1. **P9 与 P1 是同一个根因的两面**（全局事务锁 + 广播），且触发频率最高——每次下断点都会走。
2. **P8 是最隐蔽的一条**：它需要「pending MTF 未清」与「下一条指令是 VMCALL」同时成立，而 Dbgk 驱动正是高频发 VMCALL 的组件，所以并非小概率。

## 4 已排除项（避免误判，逐一给依据）

| 曾被怀疑的机制 | 结论 | 依据 |
| --- | --- | --- |
| 时钟中断被 VMM 拦截后丢失 | **排除** | `external_interrupt_exiting = false`，全仓库唯一赋值 `VmcsControls.cpp:241`，运行期从不打开 |
| VMM 把来宾 IF 清 0 | **排除** | `GUEST_RFLAGS` 在 VM-exit 路径只有读，唯一写在初始化 `VmcsGuest.cpp:79` |
| `recover_nmi_blocking` 置 `blocking_by_nmi` 导致中断被阻塞 | **排除** | `blocking_by_nmi` 只阻塞 NMI/SMI，不阻塞可屏蔽中断（时钟中断是可屏蔽中断） |
| MTF 置位期间时钟中断被饥饿 | **不成立（作为独立通路）** | MTF 在 `VmExitException.cpp:117` 的 MTF handler 入口即被清除，每次只覆盖一条指令，不足以造成秒级饥饿；但 **P10** 的零前进循环成立 |
| `virtual_interrupt_delivery` / TPR shadow / APIC 虚拟化误配 | **排除** | 三者均为 `false`（`VmcsControls.cpp:104/154/168`），不参与中断投递 |

## 5 只针对 0x101 的修复（按「直接消因」排序）

| 序号 | 动作 | 消除的通路 | 风险 |
| --- | --- | --- | --- |
| F1 | **删除 `wait_for_page_quiescence` / `wait_for_function_quiescence` 的跨核等待**，改为「置 `removing` + 摘链 + 挂本核待回收链，引用归零后由本核下次退出回收」（引用计数已存在，用一次 `InterlockedCompareExchange(...,0,0)==0` 判定，不阻塞） | **P7、P8** | 中（须保证不漏减引用） |

| F3 | **缩小事务锁持有范围**：锁内只保留指针替换（`swap_pml1_and_invalidate_tlb` 的条目写入），把整页 guest 读、split、池分配、逐核 commit 移到锁外 | **P1、P5** | 中 |

| F5 | **`outFile` 门闸由「IRQL」改为「根态标志」**（在 `vcpu` 上维护 `in_root_context`，VM-exit 入口置位、VMRESUME 前清零） | **P3** | 低 |
| F6 | **池耗尽改为「失败返回」**，禁止在根态隐式 `ExAllocatePool`（对照 HyperPlatform：耗尽直接 bugcheck，绝不阻塞） | **P4** | 低 |

| F8 | **限次保护改为「按 GPA+qualification 集合」而非「连续相同」**，或对同一页的重复 violation 单独计数，使交替循环也能被捕获并转为可控失败 | **P10** | 低 |

## 6 待确认（只列与 0x101 直接相关的）

1. **实机 0x101 转储的 Arg4（挂起处理器索引）与 Arg3（PRCB）**：单核挂起 → 指向 P1/P2/P3/P4 这类「单核长操作」；**多核同时挂起 → 直接坐实 P9（广播 + 全局锁）**。这是最有判别力的一条信息。
2. 是否抓到过 `0x00020001`（Arg1 = `vmx_fatal_unhandled_ept_violation` = 7）与 0x101 **交替出现**？若交替 → 坐实 **P10**（同一缺陷因 GPA 是否交替而报不同码）。
3. `VMCALL_DUMP_VMCS_STATE`（`VmcallDispatch.cpp:377`）在实机上是否被频繁调用？若调试器会周期性 dump，则 **P2** 优先级应提到最高。
4. 实机是否出现过 `FAST_FAIL_INCORRECT_STACK`？若有 → **P3** 优先级应提到最高。
5. `mtf_reference_count` 是否存在**未配对的递增**（即引用泄漏）？若有，则 **P7/P8 从「需要条件」变为「必然」——这是最需要静态验证的一点。** 建议对 `mark_pending_mtf_page` 的每一次成功返回，逐一核对是否存在对应的 `clear_pending_mtf_metadata`。
