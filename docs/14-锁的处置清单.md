## 〇之二 更正：P2 的严重度被我高估了

**原判断**（`docs/10` P2、本文原第 2 项）：「`vmcs_dump_lock` 内约 150 次 `DbgPrint`，带调试器时持锁可达数百毫秒到秒级」。

**核对后的事实**：`LogDump` 在 `Common/Ring0/SymbolicAccess/Utils/Log.h:60` 的 `#else` 分支里展开为**空宏**，而 `DEBUG_WinSys` **全仓库从未定义**（只有 `Log.h:5` 一行被注释掉的 `//#define DEBUG_WinSys`；`VT_Driver.vcxproj` 只定义 `DEBUG;_DEBUG_LOG`）。

因此 `dump_vmcs()` 当前实际执行的是：
- **2 行**真正的 `DbgPrintEx`（`HypervisorVmcsDump.cpp:14` 与 `:211` 的首尾分隔线，**不受宏控制**）
- **150 次 VMREAD**（微秒级）

→ **`vmcs_dump_lock` 的持锁时间本就极短，P2 不是有效的 0x101 通路，应下调为「多余锁清理」。**
第 2 项仍值得删（它本来就是不必要的锁），但**不能再作为 0x101 的修复理由**。

> 方法论提醒：`LogDump` / `LogError` / `LogDebug` / `LogInfo` / `outLog` 在 `DEBUG_WinSys` 未定义时**全部是空宏**；只有 `sLog`（`_SERIAL_DEBUG_LOG`）与 `outFile`（`VtLoadWriteLog`）是真实输出。分析根态耗时前必须先确认宏是否生效。

## 一 直接删除（3 项）

### 1. `g_vmx_init_lock` —— 已删除 ✅

| 项 | 内容 |
| --- | --- |
| 引入节点 | **76b7072**（2026-09-13），提交理由原文：「P0-003：多核 VMX 初始化自旋锁，防止**并发** VMXON 竞态条件」 |
| 为什么可以删 | `initalize_vcpu` 全仓库**只有 1 个调用点**：`Vmm/VmmEntry.cpp:41`。该调用点在一个**顺序 `for` 循环**内，每轮用 `KeSetSystemGroupAffinityThread` 把**同一个线程**绑到目标核（`:38`），执行完再 `KeRevertToUserGroupAffinityThread`（`:59`）。全仓库**没有任何** `KeGenericCallDpc` / `KeIpiGenericCall` 调用初始化路径。 |
| 结论 | **不存在并发。这把锁保护的是一个不存在的竞态。** |
| 实际改动 | `Globals/Globals.cpp`（删定义）、`Globals/GlobalsState.h`（删声明）、`Vmm/VmmProcessor.cpp`（删 3 处 lock/unlock）。附带发现：同批引入的 `g_vmx_initialized_count` **只被递增、无任何读取方**（也是死代码，本次保留未动，已在注释标注）。 |

### 2. `vmcs_dump_lock` —— 已删除 ✅（0x101 相关性已下调）

| 项 | 内容 |
| --- | --- |
| 引入节点 | **a9ef865**（最早的「重构项目」节点） |
| 为什么可以删 | 用一把**跨核自旋锁**保护调试输出，代价大于收益。且经核对（见 §〇之二），锁内绝大多数行是空宏，持锁时间本就极短。 |

### 3. `eptWatchTransaction_lock` —— **未改，需先满足 3 个前置条件**

| 项 | 内容 |
| --- | --- |
| 引入节点 | **ffd837b**（定义于 `Globals/Globals.cpp:15`），**81660d0** 正式投入使用 |
| 为什么该删 | 它的存在**只因为一个设计选择**：`Ept/Watch/EptWatchActivation.cpp:98-109` 与 `EptWatchBreakpointInstall.cpp:137-147` 会从**当前核**循环改写**所有核**的 EPT。但 EPT 本来就是**每核独立**的。 |
| 历史证据 | `81660d0` 的实际 diff 是 `lock(&eptWatchList_lock)` → `lock(&eptWatchTransaction_lock)`——**把重活从表锁搬到新锁，结构原封不动**。 |
| 覆盖通路 | 0x101 的 **P1（锁内重活）** 与 **P8（与忙等互相等待）** |

**它现在是「承重」的，不能直接删。** 删除前必须补齐以下 3 个前置条件，否则会引入真实的并发缺陷：

| 前置 | 为什么必须 | 位置 |
| --- | --- | --- |
| **前置 1** | `ept_watch_activate_internal` 的「查找或创建页记录」不是原子的：两个并发事务对同一页都会「查不到 → 各自创建 → 各自插入」→ **重复页记录**（`has` 计数错乱、删除路径只摘掉一条）。需改为**幂等创建**（分配在锁外，插入前在 `hooked_page_list_lock` 内复查，若已存在则丢弃自己新建的）。 | `Ept/Watch/EptWatchPageInstall.cpp:65-155` |
| **前置 2** | 删除路径 `ept_watch_deactivate_internal` **遍历链表时不持 `hooked_page_list_lock`**（`EptWatchDeactivate.cpp:19-100`），只在 `remove_hooked_page` 内部才加锁。事务锁一旦移除，他核的读路径就可能与这次遍历并发 → **UAF**。需让遍历也在锁内（或改成「先摘链再加锁」）。 | `Ept/Watch/EptWatchDeactivate.cpp:19-100` |
| **前置 3** | 读路径 `get_hide_software_breakpoint`（`EptWatchBreakpoints.cpp:205-235`）遍历 `hooked_page_list` **完全不持锁**——这正是 `ExecuteReadSoftwareBreakpoint` 要用事务锁包住它的原因。需改为持 `hooked_page_list_lock`。 | `Ept/Watch/EptWatchBreakpoints.cpp:205-235` |

**并且需要先定 A/B 路线**（见 §五 与 `docs/12` §六）：

- **(A) 本核改本核**：跨核操作改为逐核定向提交 → 事务变成「每核事务」，用该核的 `hooked_page_list_lock` 即可覆盖，全局事务锁彻底消失。
- **(B) 保留一核改全核**：则全局互斥**仍然需要**，只能把互斥**移到 guest 侧**（在 `DbgkSysWin10/11/Hvm/HypervisorGatewayApi.cpp` 的 EPT 变更广播外加一把串行化锁，那里的上下文允许阻塞），root 侧的事务锁才可删。

**两条路线二选一，不能混。** 且本环境无法编译，建议改动后由你在本机构建验证。

## 二 降级为「每核私有」（2 项，锁本身消失）

### 4. `eptWatchList_lock` —— 降级为每核 watch 表

| 项 | 内容 |
| --- | --- |
| 引入节点 | **a9ef865** |
| 为什么可以降级 | 它保护的是全局 256 项 `eptWatchList[]`（`Globals/Globals.cpp:16`）。**这个数组之所以是全局的，是设计选择的结果，不是必须。** EPT 既然每核独立，watch 表也应该每核独立——锁自然消失。 |
| 怎么改 | 把 `eptWatchList[]` 移入 `__ept_state`（每核一份）。此后所有 `eptWatchList[ID]` 的访问都是本核访问。 |
| 风险 | **中**。需要同步改 `Ept/Watch/*` 全部文件与 `Globals/GuestThreadState.cpp`、`Cr3/Cr3Tracker.cpp` 的引用。 |

### 5. `hooked_page_list_lock` + `functions_lock` —— 改「谁拥有谁访问」

| 项 | 内容 |
| --- | --- |
| 引入节点 | 两把都是 **9ddfe75** |
| 为什么可以改 | 这两把保护的**本来就是每核 / 每页的私有数据**（`hooked_page_list` 挂在 `__ept_state` 上，`hooked_functions_list` 挂在页记录上）。它们存在**只因为存在跨核访问**：`Ept/Watch/EptWatchDeactivate.cpp:160-191` 从当前核遍历**其它核**的 `hooked_page_list`——**而且这个遍历没有持 `hooked_page_list_lock`**。**锁的存在与使用方式互相矛盾**：持锁的路径是安全的，不持锁的路径反而在跑。 |
| 结论 | 删除事务改成逐核执行（每核删自己表里的记录）后，跨核访问消失，只剩「本核 VM-exit 与 VMCALL 两条路径互斥」这一极短临界区。 |
| 风险 | **中**，与第 3 项一起改。 |

## 三 不是锁，但必须改（2 项）

### 6. `wait_for_page_quiescence` / `wait_for_function_quiescence` —— 删掉「等待」，保留「引用计数」

| 项 | 内容 |
| --- | --- |
| 引入节点 | 忙等原语出自 **ffd837b**；**9ddfe75** 封装为函数 |
| 为什么不能连机制一起删 | `9ddfe75` 的提交说明写着「修复 MTF pending 期间卸载导致的 **UAF 漏洞**」——**这是真实问题，引用计数必须留。** |
| 为什么必须删「等待」 | `Ept/EptCommon.cpp:301-329` 是 `while(...) _mm_pause();`，**无上限、无让步**，且被 `EptWatchDeactivate.cpp:74`、`EptHookCleanup.cpp:59/114/164/188` **在持有事务锁时**调用。它覆盖 0x101 通路 **P7、P8**。 |
| 怎么改（二选一） | **(a)** 改为「不阻塞回收」：置 `removing` + 摘链（新引用立即被拒）+ 挂本核待回收链，引用归零后由本核下次退出时用一次 `InterlockedCompareExchange(...,0,0)==0` 判定后回收。 **(b) 更简单**：改用 `jonomango/hv` 的「**固定数组 + 只摘链不释放**」——节点从链上摘掉但内存永不释放，**「等待引用归零」这个动作彻底消失**。 |
| 风险 | **(a) 中**（须保证不漏减引用）；**(b) 低**（结构性免 UAF，无并发窗口）。**推荐 (b)。** |

## 四 保留（2 项，但各加一条约束）

### 7. 池管理器锁（`lock_for_reading_pool` / `lock_for_request_allocation`）—— 保留，但补充路径要改（**原修法已被证伪**）

| 项 | 内容 |
| --- | --- |
| 引入节点 | `lock_for_reading_pool` 出自 **a9ef865**；`lock_for_request_allocation` 出自 **1e70867** |
| 为什么保留 | 池是**真正的全局共享资源**，锁本身合理。 |
| 要改的是**调用位置** | `PoolManager/poolmanager.h:130-136` 在池耗尽时会同步 `request_allocation` + `perform_allocation` → `ExAllocatePool*`，而 hook/watch 安装全走这条路；若该路径落在根态（IF=0）即构成 0x101 通路 **P4**。 |
| **⚠️ 原修法（「耗尽即失败返回」）不能用** | 核对调用链后证伪：`perform_allocation()` 全仓库只有 **2 个调用点** —— `PoolManager/PoolLifecycle.cpp:65`（初始化期填充预分配池）与 `poolmanager.h:134`（就是这个根态回退）。`poolmanager.h:144` 的「排队请求」**只入队、没有任何地方执行它**。→ **一旦初始池被消费完，唯一补充来源就是这个回退；改成失败返回会让安装永久失败。** |
| **正确修法** | 把补充动作移到**安全上下文**：由 guest 侧驱动（普通线程，允许 `ExAllocatePool`）触发，root 侧只把已分配内存挂进池。接口其实已留但未实现 —— `HypervisorGateway/hypervisor_gateway.cpp:203` 的 `send_irp_perform_allocation()` 是空实现、直接 `return false`。 |
| 风险 | 中（属设计补齐，非一行改动） |

### 8. `g_TrackerLock` —— 保留，但先决定功能是否保留

| 项 | 内容 |
| --- | --- |
| 引入节点 | **ba4c0d1** |
| 现状 | `Cr3TrackerObserve` 全工程**只剩 1 个调用点**（`VmExit/VmExitEpt.cpp:120`）；CR3-load exit 路径（`VmExitControl.cpp:38-39`）只 Publish/Remember **不 Observe**；`Cr3TrackerWorker.cpp` 的 `TryConsumeCandidate` **无任何调用者**。即「观察/更新」侧已实际不生效，只有 `Acquire`/`Release` 还被 watch 安装路径使用。 |

## 五 附带删：整套广播（不是锁，但同一根因）

### 9. `KeGenericCallDpc` 全核广播 + 广播侧事务模式 —— 随第 3 项一起删

| 项 | 内容 |
| --- | --- |
| 引入节点 | 广播出自 **a9ef865**；广播侧事务模式（`KeSignalCallDpcSynchronize` 选举属主）出自 **cb1197e**（「将 Dbgk 全核 EPT 操作串行为单次事务，消除 N² VMCALL」） |
| 为什么删 | `KeGenericCallDpc` 是 `KeIpiGenericCall` 的底层：在 **`IPI_LEVEL`** 运行回调、**设屏障等全部处理器到达**，回调约束「等同 bug-check 回调」。而 `CLOCK_LEVEL=13 < IPI_LEVEL=14` → **时钟中断被屏蔽**。本项目在回调里发 VMCALL 进根态（`IF=0`）并抢全局事务锁 → **双重屏蔽**。这是 0x101 通路 **P9**（频率最高，每次下断点都走）与 **P12**。 |
| 为什么可以删 | 既然 EPT 每核独立、改成逐核定向提交，就**不需要「全核同时改」**。 |
| 怎么删 | 保留「逐核定向提交」用的亲和性绑定循环；把「改完通知其它核刷新」改为 **KVM 式请求 + 惰性刷新**（per-CPU `EptFlushPending` 位 + `mode` + Dekker 防漏 IPI，在 `VMRESUME` 前补做）。**注意**：若选择保留「一核改全核」，则逐核 INVEPT 必须保留（当前广播路径是**每个核都各自 INVEPT**，功能正确，不要误删）。**两条路线二选一，不能混。** |
| 风险 | **中**。 |

## 七 为什么历史会走到这一步（一句话）

> main 全 **26 个节点**里，**7 个新增了锁/同步机制，没有任何一个节点删除过任何一把锁**。
> 而 `81660d0` 与 `5700be5` 这两个「把重操作移出表锁」的节点，做的事是**把重活从一把锁搬到另一把新锁**。
>
> **每次都在缩短一把锁的持有时间，从未质疑「为什么需要一把全局锁」。**
