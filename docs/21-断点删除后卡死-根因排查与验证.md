# 21 断点删除后卡死 —— 根因定位、代码验证与修复

> 触发场景（用户报告）：`x32dbg` / `x64dbg` 下断点调试一段时间后，**删除所有断点**，被调试进程无法恢复、持续卡住；
> **调试器本身正常（UI 可操作）**，只有被调试进程不前进。
> 前置：`docs/12`（0x101 最终结论）、`docs/20`（CE/x64dbg/x32dbg 全量适配）。

---

## 0 一句话结论

> **根因是「INT3 读取回填」与 x64dbg/TitanEngine 的断点存在性校验互相冲突。**
>
> x64dbg 删除软件断点时会先调用 `IsBPXEnabled(addr)`，而该函数**必须读到 0xCC** 才认为断点已启用；
> 只有它返回 true，`DeleteBPX` 才会把原字节写回目标内存。而本项目的伪页设计 + 读取回填保证了
> **任何人都读不到 0xCC**（回填的是原字节），于是：
>
> `IsBPXEnabled → false` ⇒ `DeleteBPX` **跳过写回** ⇒ 本 Hook 的隐藏 INT3 记录与 VT 侧 EPT watch
> **永远不会被删除**，而 x64dbg 的本地记录照样被 erase ⇒ 被调试进程反复命中残留的 0xCC、无法继续执行。
>
> **已修**：让「断点存在性校验读取」（长度 2、起始于断点地址）返回 0xCC，其余读取仍返回原字节。
> 被调试进程的隐藏效果不受影响（它由 EPT 伪页负责，与本次改动无关）。

`TitanEngine/stdafx.h:263`：`#define UE_MAX_BREAKPOINT_SIZE 2` —— **校验读取固定为 2 字节**。

### 1.2 本项目的读取回填

`Hook/HookCallSet/Hooks/HookManager/HiddenInt3MemoryRead.cpp`（修改前）把**所有**覆盖到断点的读取都回填成 `OriginalBytes`：

```cpp
readBytes[offset] = breakpoint.OriginalBytes;   // ← 2 字节的校验读取也被回填成原字节
```

叠加 EPT 伪页设计（`changed_entry.read = 0 / write = 0`，见 `Ept/Watch/EptWatchBreakpoints.cpp:149-153`），
**guest 侧任何读取都会触发 EPT violation 并被换回原页** —— 即无论走哪条路，`ReadData[0]` 都不可能是 0xCC。

### 1.3 同一缺陷的第二个受害者：步过

`x64dbg-development/src/dbg/breakpoint.cpp:576-582`（`BpSetSingleshoot`，步过用的临时断点重装）：

```cpp
if(IsBPXEnabled(Address) && bpInfo->enabled)
{
    if(!DeleteBPX(Address)) ...
    if(!SetBPX(Address, bpInfo->titantype, cbUserBreakpoint)) ...
}
```

`IsBPXEnabled` 恒为 false ⇒ 这段重装逻辑**从不执行** ⇒ 步过的临时断点无法重新武装。

### 1.4 对照验证：为什么 CE 不受影响

CE 恢复原字节是**无条件**的（`cheat-engine/Cheat Engine/debughelper.pas:1526-1532`）：

```pascal
if breakpoint^.breakpointMethod=bpmInt3 then
begin
    vpe := ... VirtualProtectEx(...);
    WriteProcessMemory(processhandle, pointer(breakpoint.address), @breakpoint.originalbyte, 1, bw);  // 无校验
    ...
end
```

→ **CE 的删除路径不依赖 0xCC 校验，因此正常**；只有走 TitanEngine `DeleteBPX` 的 x64dbg/x32dbg 会中招。
这与用户「x32dbg/x64dbg 卡住」的报告完全一致。

## 2 修复

`Hook/HookCallSet/Hooks/HookManager/HiddenInt3MemoryRead.cpp`：

```cpp
constexpr SIZE_T kBreakpointVerifyReadSize = 2;   // == TitanEngine UE_MAX_BREAKPOINT_SIZE
constexpr BYTE   kInt3Opcode = 0xCC;
const bool is_breakpoint_verify_read =
    actualBytesRead == kBreakpointVerifyReadSize &&
    ToAddressValue(baseAddress) == breakpoint.VirtualAddress;

readBytes[offset] = is_breakpoint_verify_read ? kInt3Opcode : breakpoint.OriginalBytes;
```

**为什么用「长度 == 2 且起始地址等于断点地址」作为判据**（逐条核对，无冲突）：

| 读取方 | 长度 | 是否起始于断点地址 | 本判据下返回 | 期望 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `IsBPXEnabled`（断点校验） | 2 | 是 | **0xCC** | 0xCC | ✅ 修复点 |
| 反汇编 `MemRead`（`disasm_fast.cpp:103/111`） | 16 / 64 | 是 | 原字节 | 原字节 | ✅ 反汇编仍显示原始指令 |
| 内存操作数（`disasm_helper.cpp:190-200`） | 1/4/6/8 | — | 原字节 | 原字节 | ✅ |
| `oldbytes` 捕获（`cmd-breakpoint-control.cpp:122`） | 2 | 是 | 原字节 | 原字节 | ✅ 见下 |
| `BpEnable` 的 `oldbytes` 重读（`breakpoint.cpp:408`） | 2 | 是 | 原字节 | 原字节 | ✅ 见下 |
| CE 捕获原字节（`debughelper.pas:1663`） | 1 | — | 原字节 | 原字节 | ✅ |

- **`oldbytes` 捕获为何安全**：`cbDebugSetBPX` 的顺序是 `BpGet` → **`IsBPXEnabled`（为 false 才继续）** → `MemRead(oldbytes, 2)` → `BpNew` → `SetBPX`。
  即执行到 `MemRead` 时**必然不存在隐藏 INT3**，本判据不生效，拿到的仍是真实原字节。
- **`BpEnable` 的重读为何安全**：重读发生在断点被重新**启用**时；禁用断点会走 `DeleteBPX`，修复后写回必然执行、隐藏 INT3 已被删除，因此同样不存在隐藏 INT3。
- **被调试进程的隐藏效果不受影响**：本 Hook DLL 只注入**调试器进程**，被调试进程的读取完全不经过它；对调试目标而言，0xCC 由 EPT 伪页隐藏（伪页 r/w=0，任何读取触发 EPT violation 后由 VMM 换回原页），与本次改动无关。

**已知残留（可接受，需记录）**：若某次「长度为 2 且恰好起始于隐藏断点地址」的读取属于**内存操作数读取**（而非断点校验），第一字节会被返回为 0xCC，显示值偏差 1 字节。该情形要求「断点地址同时被当作 2 字节数据操作数读取」，实际极少出现，且只影响显示。

**维护提示**：本判据耦合 TitanEngine 的 `UE_MAX_BREAKPOINT_SIZE`。若上游改动该常量（`TitanEngine/stdafx.h:263`），需同步调整 `kBreakpointVerifyReadSize`。已在代码注释中标明出处。

## 3 对前几轮改动的验证结论

### 3.1 已实际编译通过

`VT_Driver` / `DbgkSysWin10` / `DbgkSysWin11` / `Hook` / `Loader` / `UnrealDbgDll` 的 **x64 Release 全部构建成功**。
Win32 配置报 `'Win32' is not a valid architecture for Kernel mode drivers` 属内核驱动不支持 Win32 的既有现象。

### 3.2 跨核 EPT 刷新：设计正确（此前怀疑已排除）

断点安装/删除的调用链：

```
Hook/Dbgk ── current_vmcall() ──┬─ IsEptMutation(cmd)==false → 单核 VMCALL
                                └─ IsEptMutation(cmd)==true  → hvgt::vmcall() 广播
```

`DbgkSysWin11/Hvm/HypervisorGatewayBroadcast.cpp:233 broadcast_vmcall` 的实现是
**「屏障选举属主 → 只有属主执行 VMCALL（改所有核的 EPT）→ 第二次屏障 → 每个核各自执行 `VMCALL_INVEPT_CONTEXT` 刷自己的 EPT TLB」**，
且 `Common/Ring0/Hvm/VmcallDispatchPolicy.h` 的 `IsEptMutation()` 已包含全部 watch 命令。
→ **不存在「只刷本核 TLB」的缺陷；`docs/12` 的 F5/F8/F9/P10/F1 均已落地。**

### 3.3 本轮改动的语义核对

| 改动 | 结论 |
| --- | --- |
| 执行型硬件断点桥接（G1） | 幂等守卫 `IsCurrentHardwareBreakpointState` 已比较 `rwCodes[]`；`NewGetThreadContext` 按 `debugRw/debugLen` 回填 DR7 的 RW/LEN，RW=00 正确 |
| `MOV DR` 虚拟化（G2/G3） | 六种场景（写/读 DR0-3、写 DR6、读 DR7 含 GD、GD 一次性语义、guest 自身断点命中、DR4/5 #UD）逐条与 SDM 对齐 |
| VM-exit 序言 `DR7_FIXED_1` | 读 DR7 安全（`GUEST_DR7` 已剔除 GD）；无需恢复，VM-entry 会从 `GUEST_DR7` 重载 |
| 单步状态捕获（G5） | 只增加状态捕获，不改变事件流 |

**结论：前几轮改动未发现会引入本卡死症状的回归。**

### 3.4 附带修复：EPT 监视路径的「无进展自旋」

`VmExitEpt.cpp` 中 `mark_pending_mtf_page` 失败即等价于「该页已被删除事务置 `removing`」
（`Globals/MtfPendingState.cpp:41`、`:89` 是仅有的两个 `return false` 点）。这些失败分支原先直接
`handled_return`（或由 `EptWatchInt3Execute` 返回 true 间接导致 `handled_return`）——既不改变状态
也不让来宾前进，来宾会立刻重试同一条指令并再次走到同一分支，构成**结构性无限自旋**。

本轮已改为走 `unhandled` 路径（释放热引用 → 按页计数 → 本地 INVEPT → 来宾重试）的共 **3 处**：

| # | 位置 | 原行为 | 现行为 |
| --- | --- | --- | --- |
| 1 | `VmExitEpt.cpp` bpType==3 分支 | `set_mtf(false)` + `handled_return` | `unhandled_after_release` |
| 2 | `VmExitEpt.cpp` 非 bpType==3（普通 watch）分支 | `set_mtf(false)` + `handled_return` | `unhandled_after_release` |
| 3 | `EptWatchInt3Execute.cpp`（经返回值间接决定） | `return true` → 调用方 `handled_return` | `return false` → 调用方 `unhandled_after_release` |

删除事务完成后重试即成功；条件持续存在时也会在 64 次后收敛为可诊断的 `vmx_fatal_error`。

> 说明：该自旋**不是**本次卡死的根因（若发生，删除断点用的 `KeGenericCallDpc` 全核屏障会一起挂住，调试器 UI 也会无响应），
> 但它是真实的稳定性缺陷，且与本场景同属「删除断点」路径，故一并修复。

> **⚠️ 本轮未覆盖的同类点（待定）**：`VmExitEpt.cpp` 还有 2 处失败分支仍是
> `goto handled_return` 且不做任何状态推进 —— ① `EPTO_HOOK_FUNCTION` 执行违规分支（本文件 `:99`）、
> ② 普通 EXECUTE watch 的 `changed_entry.page_frame_number == 0` 分支（本文件 `:123`）。
> 失败条件与上表完全相同（页面正在被删除），因此**属同一缺陷类**。本轮为忠实移植分支改动而**未改动**，
> 是否一并收敛由后续决定；若要改，修法与本表 1、2 完全一致。

## 5 验证清单

1. 全量重建 x64 Release：0 error / 0 warning。
2. **x64dbg / x32dbg 各下 10 个 INT3 断点 → 反复命中/继续 100 次 → 删除所有断点 → 目标应立即恢复正常执行**（本次修复的回归点）。
3. 断点**禁用/启用**（`bpd`/`bpe`）各 10 次 → 断点仍可命中，且删除后内存中无残留 0xCC。
4. 步过一条 `CALL`（`F8`）100 次 → 每次都停在正确位置（验证 `BpSetSingleshoot` 的重装逻辑已恢复）。
5. 反汇编窗口在断点地址处**仍显示原始指令**（不应显示 `int3`）。
6. 断点地址处读取内存（`Ctrl+G` 转储）应显示原始字节，不应出现 0xCC。
7. CE 回归：设/删 INT3 断点各 10 次（CE 路径本就不依赖该校验，用于确认未引入新问题）。
8. 叠加硬件断点（`bph` / `bphws addr, r`）后再执行步骤 2。
