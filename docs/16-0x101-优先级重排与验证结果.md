# 16 0x101 优先级重排与验证结果

本文记录本轮对前序结论的**修正**，以及由此重排的优先级。修正的原因都是「实测/核对后发现原判断不成立」。

---

## 1 关键判据修正：**有界操作不可能触发 0x101**

0x101 的判据是「某处理器在**时钟看门狗间隔**内没响应时钟中断」。该阈值是**秒级**（`docs/12` §二 引 Microsoft 文档：Arg1 = 时钟中断超时间隔，以标称时钟周期为单位）。

→ **只有「无界」或「会阻塞」的操作才可能触发 0x101。耗时为几十毫秒的「有界」操作，无论它持多少把锁，都到不了看门狗阈值。**

这条判据把 `docs/10` 的 12 条通路重新分成两类：

| 类别 | 通路 | 是否 0x101 成因 |
| --- | --- | --- |
| **有界**（十毫秒~百毫秒级） | **P1** 事务锁内重活、**P2** `dump_vmcs`、**P5** 持锁整页读、**P9** IPI 全核广播 | **否** —— 是性能/时延问题，不是 0x101 |
| **无界/阻塞** | **P3** 根态文件 IO、**P4** 池耗尽根态分配、**P6** `spinlock` 无上限、**P7/P8** 跨核忙等、**P10** 交替 GPA 零前进、**P11** `#GP` 风暴、**P12** 卸载路径跨核等待 | **是** |

> **这条修正推翻了我此前把 P9 列为「最优先」的判断。** P9（`KeGenericCallDpc` 在 `IPI_LEVEL` 广播 + 抢全局锁）确实是**频率最高**的路径，但它是**有界**的（N 核 × 每核 EPT 操作的串行总时长，量级在几十毫秒），**到不了秒级的看门狗阈值**。它是真实的性能缺陷，但不是 0x101 的直接成因。

**推论：0x101 的修复目标应该是「消除无界等待与阻塞」，而不是「减少锁的数量」。**

## 2 本轮验证结果（三条修正）

### 2.1 P2 已证伪（已在 `docs/10`、`docs/14` 更正）

`LogDump` 在 `Common/Ring0/SymbolicAccess/Utils/Log.h:60` 的 `#else` 分支是**空宏**；`DEBUG_WinSys` **全仓库从未定义**。`dump_vmcs()` 当前只执行 2 行真 `DbgPrintEx` + 150 次 VMREAD（微秒级）。

### 2.2 P3 是**潜在**风险，不是现实风险

核查了 `outFile`（= `VtLoadWriteLog`，真实文件 IO）的**全部 155 个调用点**，按文件分布：

```
35 Ept/Build/EptPageTables.cpp      （EPT 构建 + cleanup_page_table）
26 Vmm/VmmContext.cpp               （free_vmm_context）
23 Globals/HostTables.cpp           （Host 页表构建）
19 Vmm/VmmProcessor.cpp             （逐核初始化）
16 Driver/DriverLifecycle.cpp       （DriverEntry / Unload）
13 Vmm/VmmEntry.cpp                 （vmm_init）
11 Vmm/VmmVcpu.cpp / 11 Vmm/VmmHostPageTables.cpp
 9 Globals/VmxState.cpp / 7 Vmcs/VmcsFill.cpp / 5 Vmcs/VmcsHost.cpp
 4 HypervisorRoutines/HypervisorVmx.cpp（能力检查）
 2 VmExit/VmExitTelemetry.cpp        ← 唯一在 VmExit/ 目录下的
```

逐条核对结论：
- `cleanup_page_table()`（`EptPageTables.cpp:190`）只被 EPT 构建失败路径与 `VmmContext.cpp:142` 的 `free_vmm_context` 调用 → **初始化/卸载上下文**。
- `VmExitTelemetryDump()`（`VmExitTelemetry.cpp:6`）**只被 `VmmContext.cpp:98`（`free_vmm_context`）调用**，不在 VM-exit 热路径。
- 热路径里的 `record_vmexit_telemetry()`（`VmExitDispatcher.cpp:57`）**只写内存计数器，不调用 `outFile`**。
- `HypervisorVmx.cpp` 的 4 处位于 `required_vmx_capabilities_supported()` → 初始化上下文。

→ **`outFile` 目前不在 VM-exit / 根态路径上可达。** P3 是**潜在隐患**（后续若有人在根态加一行 `outFile` 就会中招），**不是当前 0x101 的成因**。作者此前已把统计输出搬到 `cleanup_page_table`（`docs/04` B16 有记录），这一步做对了。

### 2.3 P4 的朴素修法（「池耗尽即失败」）会**破坏功能**，不能用

`docs/14` 原第 7 项写的是「池耗尽改为失败返回」。核对调用链后发现**这会让安装永久失败**：

- `perform_allocation()` 的调用点只有 **2 处**：`PoolManager/PoolLifecycle.cpp:65`（初始化期填充预分配池）与 `PoolManager/poolmanager.h:134`（就是那个根态回退）。
- `poolmanager.h:144` 的「排队请求」（`request_allocation(size, 1, intention)`）**只入队、不执行** —— 全仓库没有任何地方会去 `perform_allocation` 这个队列。
- 因此：**一旦初始预分配池被消费完，唯一的补充来源就是那个根态回退。** 把它改成失败返回，就等于「池用尽后安装永远失败」。

**正确修法**：需要一个**安全上下文的补充路径**。设计意图其实已经在代码里留了接口但没实现——`HypervisorGateway/hypervisor_gateway.cpp:203` 的 `send_irp_perform_allocation()` **是空实现，直接 `return false`**。

→ 正确做法：由 guest 侧驱动（普通线程上下文，允许 `ExAllocatePool`）通过 VMCALL/IOCTL 触发补充，**root 侧只负责把已分配好的内存挂进池**。这属于设计补齐，不是一行改动。

## 4 本轮已实施的修复：打断 P8 死锁

**文件**：`VT_Driver/VmCall/vmcall_handler.cpp`

在 `vmexit_vmcall_handler()` 的入口、**进入 `VmcallDispatch::Execute`（即获取 `eptWatchTransaction_lock`）之前**，先收敛本核尚未触发的 pending MTF：

```cpp
if (vcpu->ept_state != nullptr && vcpu->ept_state->mtf_pending)
{
    vmexit_monitor_trap_flag_handler(vcpu);
}
```

**为什么这样能打断死锁**：

```
修复前：
  CPU A：持 eptWatchTransaction_lock → ept_watch_deactivate_internal(CPU B 的页)
         → wait_for_page_quiescence：自旋等 CPU B 的 mtf_reference_count 归零
  CPU B：有 pending MTF（page_to_change 已登记，引用已 +1），但下一条指令是 VMCALL
         → VM-exit reason = VMCALL（不是 MTF）→ 引用继续被持有
         → 进入 VmcallDispatch::Execute → 抢同一把事务锁 → 自旋等 A 放锁
  ⇒ A 等 B 清引用，B 等 A 放锁 → 双核 0x101

修复后：
  CPU B 在进入 VmcallDispatch::Execute 之前先把 pending MTF 收尾
         → mtf_reference_count 递减到 0 → A 的等待条件满足 → A 继续 → 释放锁 → B 继续
  ⇒ 循环被打断
```

**为什么放在这里而不是别处**：`vmexit_monitor_trap_flag_handler` 只依赖内存中的 `vcpu->ept_state->page_to_change` / `hooked_page_info->entry_address`，以及 `set_mtf()`（写本核 VMCS 主控位）与 `invept_single_context_func`，**不依赖 VMCS 处于 MTF-exit 状态**，因此从 VMCALL exit 上下文调用是安全的。

**边界说明**：本修复只打断「互相等待」这一条；若引用存在**泄漏**（某条路径漏减 `mtf_reference_count`），等待仍会无限持续——那属于另一类缺陷，需要按 `docs/10` §6 第 5 点逐点核对 `mark_pending_mtf_page` 与 `clear_pending_mtf_metadata` 的配对。

## 6 要不要调整：决策建议

**结论：要调整，但要换对象。** `docs/14` 那份「删锁清单」的隐含前提是「锁导致 0x101」；经 §1 的有界/无界分析后，**这个前提基本不成立**——锁带来的是**时延**，不是 0x101（唯一的例外是 P7/P8 那种**无界**等待）。所以清单要按下面重新取舍。

### 6.1 建议做（理由与风险都清楚）

| 项 | 理由 | 风险 |
| --- | --- | --- |
| 删 `g_vmx_init_lock` | 删的是**不存在的竞态** | 无（已完成） |
| 删 `vmcs_dump_lock` | 多余锁，锁内几乎全是空宏 | 无（已完成） |
| **打断 P8**（VMCALL 入口收敛 pending MTF） | 真实死锁，且是**无界**的 | 低（已完成） |
| **P7 忙等有界化** | 剩余项里唯一「无界 → 有界」的直接转化 | 中 |
| **P10 限次保护改按 GPA+qual 集合计数** | 永久零前进（来宾永远碰不到可投递中断的指令边界） | 低 |
| **P11 default 分支限次放行** | 同上，永久零前进 | 低 |
| **P3 加「根态标志」门闸** | 便宜，防止后续有人在根态加一行 `outFile` 就中招 | 低 |

### 6.2 需要先设计，不能拍脑袋改

| 项 | 为什么 |
| --- | --- |
| **P4 池补充移到安全上下文** | 真实成因，但原修法（「耗尽即失败」）**会让安装永久失败**（见 §2.3）；要补齐 `send_irp_perform_allocation` 的真实路径 |

### 6.3 就 0x101 而言**不需要**做（属性能优化，另立项）

| 项 | 为什么不做 |
| --- | --- |
| 删 `eptWatchTransaction_lock`（`docs/14` 第 3 项） | **有界**（几十毫秒），到不了秒级阈值。它是**时延**问题，不是 0x101 |
| `eptWatchList_lock` 降级为每核表（第 4 项） | 同上 |
| `hooked_page_list_lock` / `functions_lock` 改「谁拥有谁访问」（第 5 项） | 同上 |
| 删 `KeGenericCallDpc` 全核广播（第 9 项） | **有界**。P9 频率最高但时长有界，不是 0x101 成因 |
| 改 `spinlock::unlock` 补内存屏障 | 内存序问题，与 0x101 无关 |
| `g_TrackerLock` / `Cr3Tracker` 取舍 | 与 0x101 无关 |

> 这一栏如果做，收益是**降低时延、提升调试流畅度**，不是修 0x101。**不要用 0x101 当理由去推动结构性重构**——那是把一个大改动绑在一个它解决不了的问题上。

### 6.4 决定「做多少」的唯一关键信息

**实机上到底有没有真的出现过 0x101？**

- **有** → 需要 0x101 转储的 **Arg3（PRCB）/ Arg4（挂起处理器索引）**：
  - **多核同时挂起** → 指向 P7/P8（跨核等待）或 P9（广播）—— 但 P9 有界，所以更可能是 P7/P8；
  - **单核挂起** → 指向 P6（自旋锁持锁者异常）或 P10/P11（永久零前进）；
  - 再配合**是否同时见过 `0x00020001`（Arg1=7）** → 若交替出现，坐实 P10。
- **没有**（只是预防性担心）→ 那么按 §1 的分析，**当前代码里没有已确认的活跃 0x101 通路**（P3 不可达、P1/P2/P5/P9 有界）。此时只需做 §6.1 里那 4 项低风险防御性改动，**不需要**动 §6.3 的结构性重构。

**建议的落地顺序**：先构建验证已完成的 3 处改动（删两把锁 + P8 打断）→ 再做 §6.1 的 P7/P10/P11/P3 → P4 单独立项设计。§6.3 全部搁置。
