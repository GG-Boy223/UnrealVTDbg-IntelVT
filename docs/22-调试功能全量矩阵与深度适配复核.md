## 0 结论摘要

| 维度 | 结论 |
| --- | --- |
| **软件断点（INT3）** | 设置/命中/读回填/反汇编 全链路正确；**删除路径本轮已修**（`IsBPXEnabled` 冲突） |
| **硬件断点（DRx）** | 执行/写/读写三型全通；命中上报（DR6）正确；**仅用户态上报**（保留，见 §3.5） |
| **内存断点（PAGE_GUARD）** | **纯 guest 侧实现，本项目零干预 → 原生可用**，但未做任何适配与验证（见 §3.6） |
| **运行 / 暂停** | 运行正确；暂停依赖 `SuspendThread`+`SetBPX(CIP)`+`ResumeThread`，**依赖本轮修复才完整** |
| **单步 / 步进 / 步过 / 运行到返回** | 机制正确；步过与运行到返回**都依赖本轮修复**（前者靠 `IsBPXEnabled` 重装，后者靠 `MemRead` 读原始 `retn`） |
| **CE 查找访问/写入** | 与硬件断点同链路；**但 CE 的 DBVM 模式会与本项目争抢 VT-x** |
| **稳定性** | 本轮另修两处：EPT「无进展自旋」、命中查询的**多余跨核广播** |

## 3 已确证缺陷与处置

### 3.1 【已修·功能】INT3 删除路径与 `IsBPXEnabled` 冲突（`docs/21`）

`DeleteBPX` 仅在 `IsBPXEnabled`（要求读到 0xCC）为真时才写回原字节。原回填让 `ReadData[0]` 永远是原字节 → 写回被跳过 → 隐藏 INT3/EPT watch 永不删除，而调试器本地记录已 erase → **被调试进程反复命中残留 0xCC**。
**修复**：`HiddenInt3MemoryRead.cpp` 仅对「长度 == 2 且起始于断点地址」的读取返回 0xCC。
**连带修复**：`BpSetSingleshoot`（步过临时断点重装）恢复；暂停用的 `DeleteBPX(CIP)` 恢复。

### 3.2 【已修·功能】执行型硬件断点被静默丢弃（`docs/20` G1）

### 3.3 【已修·稳定】`MOV DR` 未虚拟化 → `DR7.GD` 宿主三重故障（`docs/20` G2/G3）

### 3.4 【已修·稳定】EPT「无进展自旋」+ 命中查询的多余跨核广播（本轮）

**(a) 无进展自旋**：`VmExitEpt.cpp` 两处 + `EptWatchInt3Execute.cpp` 一处在 `mark_pending_mtf_page` 失败时直接 `handled_return`/`return true` —— 不改变状态也不让来宾前进，来宾重试同一条指令即回到同一分支，构成**结构性无限自旋**（且因算「已处理」，`unhandled_ept_violation_count` 不递增 → 既不蓝屏也不恢复）。
→ 改为走 `unhandled` 路径（释放热引用 → 按页计数 → 本地 INVEPT → 来宾重试）。

**(b) 多余跨核广播**：`VMCALL_GET_BREAKPOINT` 原先走 `vmcall2`（逐核切亲和性、每核各跑一次 VMCALL，且要求所有核成功才返回 true），而 VMM 侧 `query_breakpoint_detected` 本身**遍历 `g_vmm_context.vcpu[]` 全数组**（`Globals/GuestThreadState.cpp:236-249`），单核执行即可覆盖所有逻辑处理器。
→ 改为 `current_vmcall`，与 `VMCALL_PEEK_BREAKPOINT`（`Hook/DebugBreak/Core/DebugHitRecords.cpp:106`）一致。
**影响面**：本函数在**每次单步**（`CaptureSingleStepDebugState`）与暂停取上下文时被调用；x64dbg 的 `cbRtrStep` 是递归步过循环，改动前会产生大量跨核切换。

> 依据（对照开源）：跨核 TLB 刷新应「请求化 / 延迟到该核下次进 guest」，而不是在每次查询时同步全核 —— KVM `kvm_flush_remote_tlbs()`→`KVM_REQ_TLB_FLUSH`、Xen `defer_flush`+`vmx_vmenter_helper()`、ACRN `ept_flush_guest()` 只置 `ACRN_REQUEST_EPT_FLUSH`（见 `docs/13` §4 范式 3）。

### 3.5 【保留·设计取舍】硬件断点仅用户态上报

`Ept/Watch/EptWatchEvents.cpp:264-281` 要求 `!kernelmode && IF=1 && CR8=0` 才置 `isBp`（之后才注入 #DB）。
**只影响 EPT-watch 式硬件断点**；INT3 走 `bpType==3` 伪页分支**完全绕过**该门闸（同文件 `:233-244`），故 INT3 在内核态也能命中。
保留理由：`inject_single_step()` 需要可安全投递的上下文，在 `IF=0`/`CR8>0`/内核态注入会落到来宾不可预期的位置。
若要支持内核态硬件断点，正确做法是**解耦「记录」与「投递」**（命中无条件记录，投递延迟到可投递时机，复用 NMI-window 机制）。依据：jonomango-hv `queued_nmis`+`nmi_window_exiting`、HyperDbg `PendingExternalInterrupts[]`+interrupt-window exiting。

### 3.6 【未适配】内存断点（PAGE_GUARD）

本项目**没有任何代码涉及 `PAGE_GUARD`**（全仓 grep 无命中）。
**判定：原生可用**。理由：PAGE_GUARD 是 **guest 页表**属性，本项目只操作 **EPT**（第二层翻译），二者分层独立；命中后由 guest 走 `EXCEPTION_GUARD_PAGE` → Dbgk → 调试器，全程不经本项目。
**但需实机验证的交互**：同一页同时存在「内存断点（PAGE_GUARD）」与「隐藏 INT3（EPT 伪页）」时，guest 页表翻译先于 EPT，顺序为 `#PF(guard)` → guest 处理清 guard 位 → 重试 → EPT `execute=0` → 换伪页 → `0xCC` → `#BP`，语义上正确但未经实测。
另注：`Hook/.../MemoryApiHooks.cpp:29-43` 的 `NewVirtualProtectEx` 在真实调用失败时也返回 TRUE，可能掩盖内存断点设置失败（见 §3.8）。

### 3.7 【环境冲突】CE 的 DBVM 模式

CE 的 `dbvm_watch_*`（`debughelper.pas:1234-1236/1274-1276`）走 **CE 自带 hypervisor（DBVM）**。VT-x 只能有一个主人，若 CE 以 DBVM 模式启动会与本项目争抢 VT-x。
**处置**：属使用约束而非代码缺陷 —— 需在 CE 中关闭 DBVM/内核模式，改用「Windows 调试接口 + DRx」路径（该路径已由 #5-#8 覆盖）。`docs/17` §4 已记录本机同时存在 `vmx86`/`LdVBoxDrv`/`winhvr` 等 VT-x 争夺者。

### 3.8 【已记录·未改】需要作者确认的三项

| 项 | 位置 | 说明 |
| --- | --- | --- |
| `NtResumeThread` 的 TL 屏蔽无解除路径 | `DbgkSysWin11/Core/DebugEvents/MemoryAndAttachEvents.cpp:281-285`；`Core/IoctlHandlers/ClientRequestHandlers.cpp:107-132` | 调用方 PID == `g_TL_Game_pid` 时 `return STATUS_SUCCESS` 但**不真正恢复线程**；且该全局**只写不读、无解除路径**（`CleanupDebugSessionState` 不清它）。若 x64dbg 的暂停流程（`SuspendThread`→…→`ResumeThread`）恰好命中该 PID，线程会永久挂起 |
| `ThreadSuspendCount` 被无条件拦为失败 | `MemoryAndAttachEvents.cpp:297-324` | 对 `ThreadSuspendCount` **无条件** `return STATUS_UNSUCCESSFUL`，并每次 `PrintProcessName`（日志噪声）。x64dbg 的 `cbDebugPause` 有 `// TODO: get suspend count instead` 注释，说明该查询被期望可用 |

## 4 需要实机验证的项

1. **暂停**：连续暂停/继续 50 次；目标处于 `GetMessage` 等待时暂停（验证 `PostThreadMessageA(WM_NULL)` 路径）。
2. **运行到返回**：`Ctrl+F9` 从深层调用返回；在 `retn` 处恰好有断点时也要正确。
3. **步过**：`F8` 步过 `CALL`/`REP MOVS`/`PUSHF` 各 50 次。
4. **内存断点**：`bpm` 设读/写/执行断点，验证命中；再在同一页叠加 INT3 断点，验证两者都命中。
5. **异常断点**：设首次机会/二次机会异常断点，验证 `EXCEPTION_*` 正常上报。
6. **CE**：关闭 DBVM 后验证「找出是什么访问了该地址」（读写/执行三型）与单步。
7. **性能**：步过 1000 次，观察是否仍有一次单步一次的跨核切换（改动后应无）。
